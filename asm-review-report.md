# ASM — adversarial code review

**Дата:** 05.10.2026  
**Режим:** read-only source review. Файлы проекта не менялись; не запускались приложение, тесты, сканеры, сетевые пробы или установщики.  
**Ограничение доказательств:** выводы ниже подтверждены статически по путям выполнения и данным; эксплуатация и фактическое поведение Windows/сетевого окружения не проверялись. Severity оценивает риск при обычном развёртывании, а не наличие уже произошедшего инцидента.

## Итог

**В текущем виде проект нельзя выпускать на машине, где есть доступ к клиентским данным или сети заказчика.** Главные причины: панель без аутентификации слушает все интерфейсы; проверки области и выключатель активных запросов обходятся отдельными стадиями; одна функция чата может читать память других объектов; загрузка страницы допускает SSRF; проверщик ответов модели исполняет Python без песочницы; вспомогательная команда удаляет выбранную базу.

- **P1 — блокеры выпуска:** 12 безусловных находок.
- **P1, условно:** 1 риск межобъектного обмена данными — это намеренная функция по тестам; блокер только при требовании изоляции заказчиков.
- **P2 — серьёзные дефекты/контроли, которые надо исправить до эксплуатации:** 17 находок.
- **P3 — надёжность, корректность и обслуживание:** 6 замечаний.

Severity не означает, что проблема уже использовалась. Положения с условием («если задан webhook», «если выбран облачный endpoint») так и помечены.

## P1 — блокеры выпуска

### P1-01. Панель по умолчанию открыта в локальную сеть без аутентификации

**Доказательство:** `asm/web.py:78-92, 483-497, 624-676, 854-869`. `serve()` по умолчанию передаёт `0.0.0.0` в `ThreadingHTTPServer`; обработчики API не требуют аутентификации. API позволяет читать цели/находки/аудит, добавлять цель и запускать скан (`/api/targets`, `/api/scan`), менять данные и вызывать агентский запуск (`/api/agent/run`).

**Воздействие:** любой клиент, который может подключиться к порту, получает доступ к данным и функциям оператора; в зависимости от состояния очереди может инициировать сетевые действия. Это не только «дашборд», а управляющий API.

**Рекомендация:** loopback как безопасное значение по умолчанию; удалённый bind — только явный opt-in. До удалённого доступа добавить аутентификацию/авторизацию, CSRF-защиту и TLS; разделить read-only и управляющие endpoints. Не считать скрытие адреса или брандмауэр заменой аутентификации.

### P1-02. Проверка области — advisory, а не fail-closed enforcement

**Доказательство:** `asm/store.py:326-334` нормализует цель, но не проверяет формат/область; в `asm/stages.py:880-930` выполняется разрешение имён в IP без повторной проверки каждого результата на scope. Сопоставление host/IP в `asm/gate.py:280-287,320-354` при несовпадении предупреждает, но не блокирует. Расширение по PTR/именам/SAN и связанные этапы находятся, в частности, в `asm/stages.py:831-859,964-991`.

**Воздействие:** фактический адрес назначения или автоматически добавленное имя могут оказаться вне согласованной области, хотя исходная цель выглядела допустимой. Частный IP сам по себе не обязательно запрещён — дефект в отсутствии проверки против scope оператора для всех фактических назначений.

**Рекомендация:** один центральный scope-enforcer для исходного target, всех DNS-ответов, PTR/SAN/ASN-расширений, IP и каждого redirect. Сверять адрес непосредственно перед соединением; несовпадение/неопределённость — блокировать, а не только логировать.

### P1-03. Автоматическое расширение может перейти к домену с похожим суффиксом

**Доказательство:** `asm/stages.py:457`, `asm/estate.py:90-91,185-189`: проверка SAN использует `endswith(root)` без требования границы DNS-метки.

**Воздействие:** имя наподобие `not-example.com` может пройти проверку как дочернее для `example.com`, попасть в расширение и затем в дальнейшие стадии. Это способно вывести анализ за пределы исходного домена.

**Рекомендация:** сравнивать точное имя или суффикс `"." + root` после нормализации IDNA/регистра и завершающей точки; затем всё равно применить P1-02 к DNS-результату.

### P1-04. Redirect не проходит повторную проверку scope

**Доказательство:** `asm/engines.py:965-968`; браузерный транспорт разрешает redirects в `asm/stealth.py:274-295`, стандартный opener — в `asm/stealth.py:313-328`. После перехода на новый host код не делает повторного scope-check.

**Воздействие:** URL в области может перенаправить HTTP-клиент на другой host/IP. Запрос, включая HTTP/TLS-пробы и сканерные обращения, продолжится к новому назначению.

**Рекомендация:** запретить redirects по умолчанию либо валидировать каждую ступень до запроса; ограничить смену host и запретить переход на private/link-local/loopback, если это не разрешено scope.

### P1-05. `ASM_ACTIVE_SCAN=0` не выключает все активные сетевые запросы

**Доказательство:** настройка задаётся в `asm/scan.py:44-46`, но Nmap `-sV` запускается в `asm/stages.py:1045-1062` без проверки `L["active_scan"]`. Лёгкие HTTP/TLS-пробы формируются и выполняются через `stage_probe_light`, `stage_web_httpx` и `stage_probe_gap_fill` (`stages.py:716-732,1103-1158`); Nikto/Wapiti/testssl также имеют собственные флаги, но не общий `active_scan` (`stages.py:491-624`). Только `stage_active_checks` проверяет этот флаг (`:1246-1251`).

**Воздействие:** оператор может явно выключить активные проверки, но скан всё равно отправит запросы к объекту. В отчёте это дополнительно описывается как пассивный анализ (P2-12).

**Рекомендация:** применять единый kill-switch до каждой сетевой стадии/соединения. При выключении active scanning должны пропускаться все Nmap, HTTP, TLS и движковые активные запросы, а в журнале явно указываться, что именно отключено.

### P1-06. Профили и fallback допускают проверки, противоречащие заявленным запретам

**Доказательство:** `asm/active.py:47-49,158-169` включает `default-logins` в прямом Nuclei-fallback, обходя более строгую сборку аргументов в `asm/engines.py`. Профили и фильтры заданы в `engines.py:116-130`; опасные Nikto/Wapiti-модули включаются в профилях `pentest/full` в `:1193-1196,1661-1684`, а `full` снимает фильтр DoS-тегов.

**Воздействие:** credential/default-login проверки, brute-force-подобные модули или DoS-категории могут быть запущены настройкой профиля, хотя общие правила проекта и ограничения оператора их запрещают. Наличие отдельного профиля не является индивидуальным одобрением шага.

**Рекомендация:** жёсткий allowlist действий на уровне ворот; запрещённые классы удалять из всех путей, включая fallback. Для исключений — отдельное подтверждение оператора, связанное с конкретным target/action, не только `ASM_PROFILE`.

### P1-07. `ASM_COVER=vpn` не доказывает, что трафик действительно идёт через VPN

**Доказательство:** `asm/stealth.py:58-60,127-131` проверяет состояние/наличие интерфейса, а не маршрут до назначения. `require` не контролирует raw sockets и все subprocess-пути (`stealth.py:626-634`); режимы задаются в `asm/mode.py:50-56`.

**Воздействие:** интерфейс VPN может быть поднят, но маршрут к адресу объекта всё ещё пойдёт через обычный шлюз. Сканер/raw socket способен обойти HTTP-прокси и другие обёртки. Это нарушает требование не обращаться к объекту с домашнего адреса.

**Рекомендация:** egress enforcement на уровне ОС/firewall/network namespace, проверка фактического маршрута для каждого назначения и блокировка прямого выхода при `require`; покрыть дочерние процессы и raw sockets. Статус должен подтверждать маршрут/egress, а не просто наличие адаптера.

### P1-08. Stored DOM XSS через имя актива в inline-обработчике

**Доказательство:** `ui/index.html:201` функция `esc()` не кодирует `'`; в `ui/index.html:1417` `d['актив']` вставляется в одинарно-quoted JavaScript внутри `onclick`, после чего весь шаблон попадает в `innerHTML` (`:1433`). Значение цели проходит через `store.add_target()` почти без валидации (`asm/store.py:326-334`) и принимается endpoint-ом (`asm/web.py:488-497`).

**Воздействие:** специально сформированное значение актива может стать исполняемым JavaScript при открытии карточки и нажатии кнопки. При открытой без аутентификации панели это даёт путь к действиям от имени оператора в его браузере.

**Рекомендация:** не вставлять данные в inline-JS/HTML-атрибуты. Создавать элементы DOM и назначать обработчики через `addEventListener`; валидировать target отдельно от HTML-экранирования. `esc()` в текстовом контексте не подходит для JavaScript-строки.

### P1-09 (условно). Межобъектная память попадает в контекст чата

**Доказательство:** `asm/chat.py:132-148` вызывает `vector.search_all(q, k=...)`, не передавая `target_id`; инструмент зарегистрирован в `chat.TOOLS` (`:299-308`). `search_all()` по умолчанию собирает находки всех targets (`asm/vector.py:460-479,514-561`). Результат инструмента включается в сообщения следующего раунда модели (`chat.py:711-720`).

**Воздействие:** запрос по одной сессии может вернуть hostname и title находки из другого объекта. При выбранной облачной модели результат отправляется вместе с сообщениями чата. **Это не безусловный дефект:** `tests/test_core.py:1522-1641` прямо проверяет межобъектную память как намеренную функцию. Риск становится блокирующим только если разные заказчики должны быть изолированы; имеющееся общее предупреждение о передаче контекста стоит сделать конкретнее.

**Рекомендация:** зафиксировать модель данных: единый доверенный пул или изоляция по клиенту. Если нужна изоляция — обязательный `target_id`/tenant-фильтр; если общий пул намеренный — отдельное информированное разрешение на передачу результатов других объектов облачной модели.

### P1-10. Проверщик ответов модели исполняет недоверенный Python без песочницы

**Доказательство:** `tools/check-big.py:58-70` записывает извлечённый код и запускает его обычным `subprocess.run([sys.executable, path], cwd=FIX, timeout=45)`. Проверки `_static()` вызываются уже после запуска (`:152-179`) и состоят из неполных regex (`:43-48,88-96`). `cwd` и timeout не ограничивают доступ к файлам, сети, переменным окружения и дочерним процессам.

**Воздействие:** запуск ответа модели или внешнего файла может читать/изменять пользовательские файлы, похищать доступные секреты, ходить в сеть или оставлять процессы. Это выполнение кода от имени пользователя, а не «песочница на синтетических фикстурах».

**Рекомендация:** не запускать внешний код. Для проверки — AST/интерпретатор ограниченного DSL; если запуск обязателен, изолированная disposable VM/container без сети, credentials и доступа к host FS, с лимитами CPU/RAM/processes и read-only фикстурами.

### P1-11. `tools/seed-hard.py` может удалить произвольную базу из `ASM_DB`

**Доказательство:** `tools/seed-hard.py:21-31` принимает путь из `ASM_DB`, без проверки удаляет существующий файл через `DB.unlink()`, затем использует его как базу.

**Воздействие:** экспортированная в shell переменная `ASM_DB`, указывающая на рабочую базу, приводит к её необратимому удалению при запуске тестового seed-скрипта. Подтверждения или резервной копии нет.

**Рекомендация:** не удалять заданный `ASM_DB`; по умолчанию создавать уникальную тестовую БД. Для перезаписи требовать отдельный `--force` и отказывать, если путь похож на рабочую базу/находится вне тестового каталога.

### P1-12. `scan --no-wait` теряет заданные оператором лимиты области

**Доказательство:** `app.py:530-545` собирает `max_subdomains`/`max_ips`, но дочерний процесс запускается без этих параметров (`argv` содержит только target и scan ID). Он использует дефолты из `asm/scan.py:38-46`. Кроме того, `app.py:531,533` и `scan.py:64-66` используют truthy-фильтр, поэтому нулевые значения теряются.

**Воздействие:** команда с маленькими `--max-subdomains`/`--max-ips` выполняет background-скан с более высокими значениями по умолчанию; при `0` вместо отключения/нулевого лимита берётся дефолт. Это прямое расхождение фактического объёма работ с заданной границей.

**Рекомендация:** передавать лимиты дочернему процессу явно; различать `None` и `0`; валидировать отрицательные значения и сохранять точные лимиты в записи скана/аудите.

### P1-13. Установка инструментов доверяет изменяемым артефактам без проверки целостности

**Доказательство:** `bin/install-tools.sh:209-237,383-462,467-529,579-618`; используются `latest`/изменяемые релизы без единого обязательного digest/signature. libpcap загружается по plain HTTP без проверки целостности (`:512-521`); GitHub token попадает в аргументы `curl` (`:215-218`). GitHub является основным источником загрузки.

**Воздействие:** компрометация upstream/перенаправление/подмена канала может привести к выполнению вредоносного бинарника с правами пользователя; token может быть виден в списке процессов/диагностике.

**Рекомендация:** закрепить версии и SHA-256 из независимого доверенного manifest; проверять подписи там, где доступны; запретить HTTP; не передавать токен через argv; записывать происхождение и digest установленного файла. Скачивание и установка инструментов требуют явного решения оператора.

## P2 — серьёзные дефекты

### P2-01. HTTP API читает тело запроса без верхнего лимита

**Доказательство:** `asm/web.py:87-93` читает весь `Content-Length`; ограничение файла применяется позже, после чтения/JSON-разбора и base64-декодирования (`:565-587`). `ThreadingHTTPServer` позволяет обслуживать несколько соединений параллельно (`:854-869`).

**Воздействие:** большие или параллельные запросы могут исчерпать память/потоки, даже если вложение затем отклоняется как превышающее 25 MiB.

**Рекомендация:** лимитировать `Content-Length` до чтения, потоково принимать файлы, ограничить число одновременных запросов и возвращать 413.

### P2-02. `llm-probe.py` отправляет ключ на произвольный base без требования HTTPS

**Доказательство:** `bin/llm-probe.py:140-166` добавляет ключ в `Authorization` или `x-api-key`; `:169-189` делает прямой `urllib.request.urlopen()`. `main()` принимает `--base` и выводит его (`:327-364`), но не проверяет схему/host. Аналогичный прямой transport/разрешение HTTP есть в `asm/aiagent.py:426-432,714-719`.

**Воздействие:** при удалённом `http://` ключ и содержимое запроса идут открытым текстом; ошибочный или подменённый endpoint может получить ключ. Для локального Ollama HTTP может быть нужен, поэтому запрет должен учитывать loopback, а не быть безусловным.

**Рекомендация:** требовать HTTPS для нелокального адреса; отдельно allowlist-ить loopback; проверять redirects и не пересылать секрет на другой origin. Для облачных вызовов использовать единый транспорт с политикой egress.

### P2-03. `app.py --settings` и `--set` могут раскрыть секреты

**Доказательство:** `app.py:30-69` принимает любую `ASM_*` настройку из argv; argv виден в истории shell/списке процессов. `_print_settings()` печатает фактическое значение (`:148-165`) и неизвестные `ASM_*` значения (`:185-189`), включая потенциальный `ASM_LLM_KEY`.

**Воздействие:** ключи могут попасть в терминальный лог, снимок экрана, историю команд и локальные средства мониторинга процессов. Это противоречит правилу хранить облачные секреты вне проекта и не раскрывать их через панель/CLI.

**Рекомендация:** секретные имена никогда не печатать; показывать только `set/не задан` и длину. Исключить секреты из `--set`; использовать защищённый env-файл/скрытый ввод/secret store.

### P2-04. Отключена проверка TLS-сертификатов для всего транспорта `collect`

**Доказательство:** `asm/collect.py:37-40` задаёт `CERT_NONE`; общий `_http()` передаёт этот контекст для запросов с разным назначением (`:43-66`). `stealth._curl_open()` также переводит такой контекст в `verify=False` (`asm/stealth.py:274-287`).

**Воздействие:** не только самоподписанный сертификат объекта, но и внешние источники/индексы могут быть подменены MITM; от этих ответов зависят активы и оценки находок.

**Рекомендация:** проверку отключать только для конкретной inward-пробы сертификата объекта, а все outward/API-запросы валидировать штатно; явно маркировать недоверенные ответы.

### P2-05. `llm-bench.py` по умолчанию берёт реальные находки и отправляет их выбранной модели без подтверждения

**Доказательство:** `bin/llm-bench.py:170-183` извлекает настоящие находки из БД; `:497-507` выбирает их по умолчанию, если не задан `--synthetic`; `_run_once()` передаёт карточку в `aiagent.build_messages()` и далее в `_tokens()` (`:194-204`); отправка идёт в цикле `:524-555`.

**Воздействие:** заголовки, активы и факты заказчика покидают локальную машину при удалённой модели. Скрипт печатает источник данных, но не останавливается для явного подтверждения передачи; сам режим не становится синтетическим автоматически.

**Рекомендация:** синтетические данные по умолчанию; отдельные `--real-data` и `--confirm-cloud`; предупреждение до первого запроса с адресом endpoint и перечнем полей; по возможности маскировать hostnames/evidence.

### P2-06. Внутренние транспортные шаги обходят предварительную проверку бюджета

**Доказательство:** `asm/agent.py:829-896` обрабатывает `INTERNAL_IDS` и может вызвать `transport.run()` до общего budget check на `:1010-1022`. В этой ветке `spend()` вызывается только после уже отправленного действия (`:869-879`); подготовленный handoff возвращается без расхода (`:883-896`). Исключение при проверке бюджета для других путей превращается в разрешение (`:919-928,1012-1017`).

**Воздействие:** лимиты шагов/шума/хостов/файлов не являются общими для всех видов действий; внутренний шаг может пройти без проверки, а ошибка проверки ведёт к fail-open.

**Рекомендация:** проверять бюджет единообразно перед dispatch для каждого action; fail-closed при недоступности учёта; атомарно резервировать расход до запуска и фиксировать фактический результат после.

### P2-07. Статусы одобрения/исполнения не захватываются атомарно

**Доказательство:** веб-сервер многопоточный (`asm/web.py:78,854-869`). `store.agent_decide()` читает статус, а затем делает безусловный `UPDATE` без условия `WHERE status=proposed` (`asm/store.py:897-922`). `agent.execute()` проверяет `approved` в `:789-823`, но меняет статус на running позднее (`:1032`); внутренние шаги проходят отдельную ветку до такого захвата (`:829-895`).

**Воздействие:** параллельные `/api/agent/run` могут выполнить один одобренный шаг несколько раз; конкурирующие решения могут перезаписать статус. Риск особенно заметен для транспортных/неидемпотентных действий.

**Рекомендация:** атомарный compare-and-swap `UPDATE ... WHERE status='approved'` с проверкой числа затронутых строк; захват шага до любого внешнего действия; уникальный execution ID/idempotency key; транзакционная фиксация решения.

### P2-08. Остановка не гарантирует завершение всех дочерних процессов

**Доказательство:** стоп ведёт через `engines.stop_all()` и `stop_survivors()` (`asm/web.py:547-563`), а `free_run` запускает `subprocess.run(..., shell=True)` (`asm/agent.py:978-980`). Текущий process tracking не охватывает все shell/вложенные процессы и raw-socket пути (`asm/transport.py:200-215`, `asm/agent.py:978-980`, `asm/active.py:35-44`).

**Воздействие:** кнопка СТОП может остановить tracked child, но оставить его потомка/внешний процесс работающим и продолжающим сетевой трафик.

**Рекомендация:** process groups/job objects на Windows и POSIX; дерево процессов и таймауты; отмена потоков/сокетов; подтверждать стоп только после проверки нулевого числа survivors, иначе показывать блокирующее предупреждение.

### P2-09. Транспорт отключает проверку host identity

**Доказательство:** `asm/transport.py:249-255,313-320` — SSH принимает новый host key; WinRM использует отключённую TLS-проверку. Широкая AD-сборка SharpHound запускается с `-c All` (`:143-154,351-356,397-464`).

**Воздействие:** SSH/WinRM могут подключиться к подменённому хосту и раскрыть учётные данные/команды; `All` может собрать существенно больший объём directory data, чем ожидается от одного шага.

**Рекомендация:** закреплять SSH host key/fingerprint; проверять TLS/сертификат WinRM; минимизировать collection methods и передавать точный объём данных в карточку одобрения.

### P2-10. Диагностический скрипт удаляет установленный `nuclei.exe`

**Доказательство:** заголовок `bin/diag-tools.sh:5` обещает не переустанавливать инструменты и использовать временные файлы. Но `:50-52` безусловно удаляет `$BIN/nuclei.exe`, `:64` копирует туда байты dnsx, а `:91` снова удаляет файл. Позже `:157-171` запускается `install-tools.sh --only=nuclei`, что уже скачивает/переустанавливает инструмент.

**Воздействие:** запуск диагностики может уничтожить существующий Nuclei, а затем заменить его другой версией или оставить отсутствующим при сбое сети.

**Рекомендация:** никогда не занимать штатное имя бинарника; работать только в `mktemp`-каталоге и проверять отсутствие коллизии; убрать скрытый вызов установщика из диагностического сценария или вынести в отдельный opt-in.

### P2-11. `--fast` не ограничивает установку базовым набором

**Доказательство:** `bin/install-tools.sh:447-449` ограничивает только перечисленные компоненты; блоки `:579-618` всё ещё устанавливают chisel/kerbrute, Ligolo и payloads.

**Воздействие:** оператор, выбравший «fast» как лёгкий базовый режим, получает дополнительные dual-use инструменты/данные и большие побочные загрузки; имя опции не соответствует фактическому эффекту.

**Рекомендация:** `--fast` должен исключать дополнительные/internal/credential/tunnel компоненты; для них отдельный явный флаг, список и подтверждение. Показать план загрузки до скачивания.

### P2-12. Отчёт утверждает, что анализ пассивный, даже когда выполнены активные проверки

**Доказательство:** `asm/report.py:216-228` безусловно добавляет «анализ пассивный». В конвейере активные Nmap/HTTP/Nuclei и другие стадии вызываются отдельно (`asm/scan.py:109-121`).

**Воздействие:** клиент получает фактически неверное описание воздействия и методики; это может повлиять на юридическую оценку, согласование и повторный запуск.

**Рекомендация:** собирать фактический список запущенных стадий/движков и генерировать ограничения отчёта из результата, а не из фиксированной строки.

### P2-13. CSV экспорт не нейтрализует формулы

**Доказательство:** `asm/report.py:352-364` сериализует текстовые поля в CSV без escaping значений, начинающихся с `=`, `+`, `-`, `@`.

**Воздействие:** поле, контролируемое результатом скана/баннером, может при открытии файла в Excel/совместимой таблице стать формулой.

**Рекомендация:** безопасно префиксовать опасные ячейки (с учётом пробелов/табов и Unicode-вариантов), либо выдавать XLSX с явным текстовым типом; тестировать экспорт на атакующих значениях.

### P2-14. Вложения не изолированы по сессии/объекту

**Доказательство:** обработка вложений в `asm/chat.py:223-240,538-605`; API сохраняет материал через `asm/web.py:565-587`; id вложения используется без надёжной проверки соответствия текущей сессии/target (`asm/store.py:1041-1043`, `asm/mcp.py:50-51`).

**Воздействие:** некорректный или угадываемый attachment ID способен подмешать файл другого target/session; имена/пути также могут перезаписываться при совпадениях.

**Рекомендация:** связывать каждое вложение с target и session на уровне запроса; сверять владельца при чтении/удалении; генерировать безопасное уникальное имя, хранить вне пути, заданного пользователем.

### P2-15. Некорректный JSON-RPC batch может завершить MCP-процесс

**Доказательство:** `asm/mcp.py:160-170` принимает любой JSON-массив; если его элемент не `dict`, `handle(m)` падает, а обработчик исключения повторно вызывает `m.get("id")`.

**Воздействие:** строка/`null`/число в batch вызывает исключение уже внутри error-handler и завершает stdio-сервер вместо JSON-RPC ошибки на этот элемент.

**Рекомендация:** валидировать форму сообщения до `handle`; error-handler не должен читать поля у непроверенного объекта; для ошибочного элемента формировать стандартную ошибку с `id: null` и продолжать batch.

### P2-16. Аудит сохраняет URL/пути материалов целиком

**Доказательство:** `asm/store.py:345-349` записывает весь словарь `materials` в audit. Эти значения приходят из API `asm/web.py:522-529` и могут содержать URL репозитория/credential-bearing URL или чувствительные локальные пути.

**Воздействие:** секрет в URL или чувствительный путь остаётся в долговременном audit; к нему также открыт API аудита при текущем отсутствии auth.

**Рекомендация:** нормализовать типы и разрешённые поля, удалять userinfo/query secrets из URL, маскировать значения в audit и применять отдельную политику доступа/retention.

### P2-17. Уведомления условно отправляют клиентские данные третьей стороне

**Доказательство:** при заданных `ASM_TG_TOKEN/ASM_TG_CHAT` или `ASM_WEBHOOK_URL` `asm/notify.py:20-22,25-44,47-74` включает hostname цели, заголовки P0-находок и статистику и отправляет их напрямую Telegram/webhook. По умолчанию функция выключена — это условный риск, не утверждение о безусловной отправке.

**Воздействие:** включение интеграции раскрывает название клиента/хоста и детали находок выбранному внешнему сервису; отдельного redaction/подтверждения в коде нет.

**Рекомендация:** минимизировать payload, дать отдельный явный consent и dry-run/preview, документировать получателя, скрывать hostnames и не отправлять evidence.

## P3 — корректность, качество и эксплуатация

### P3-01. Fallback чтения `~/.asm-cloud.sh` в `llm-probe.py` не является shell-парсером

**Доказательство:** `bin/llm-probe.py:114-137` читает строки как одиночные `NAME=value`; не исполняет shell, не обрабатывает `;`, переменные/подстановки и shell-экранирование. В `bin/llm-ab.py:106-108` приведён пример файла с тремя `export` на одной строке.

**Результат проверки:** это **не** `source`: при уже экспортированных трёх переменных окружения функция сразу возвращает их (`llm-probe.py:116-120`), поэтому документированный вариант `source ~/.asm-cloud.sh` работает. Но если полагаться именно на fallback-парсер и использовать однострочный пример из `llm-ab.py`, значения будут разобраны неправильно.

**Воздействие:** ложное «окружение не задано» или некорректный base/model в новом окне, если файл не был `source`-нут.

**Рекомендация:** выбрать и документировать один формат: либо только простые отдельные строки `export NAME=value` с проверкой формата, либо всегда просить `source`; не пытаться частично интерпретировать shell. Не применять `eval` к файлу секретов.

### P3-02. Семантическая память — полный проход по всей БД на запрос

**Доказательство:** `asm/vector.py:460-479,514-561` загружает все findings и перебирает их для каждого `search_all`; `_t_memory()` может вызывать этот путь из чата (`asm/chat.py:132-148`).

**Воздействие:** время и память растут с историей всех объектов; фильтр `target_id` предусмотрен, но не передаётся из инструмента чата. Это одновременно performance-дефект и первопричина P1-09.

**Рекомендация:** tenant-filter до чтения, vector index/ANN backend или SQL-предварительный отбор, лимиты на размер корпуса и метрики задержек.

### P3-03. Повторный скан автоматически помечает находку `fixed` только по отсутствию в результате

**Доказательство:** `asm/stages.py:1585-1621` сопоставляет finding key/IP; если IP считался проверенным, а finding в новом наборе отсутствует, статус меняется на `fixed`.

**Воздействие:** ошибка/отключение движка, неполное покрытие порта или изменение точности обнаружения может выглядеть как подтверждённое устранение.

**Рекомендация:** различать `not observed` и `fixed`; закрывать автоматически только при валидной проверке той же поверхности и явно доказанном результате. Хранить покрытие/ошибки стадий рядом с решением.

### P3-04. Глобальная дедупликация CPE теряет привязку к нескольким объектам

**Доказательство:** `asm/stages.py:1338-1349` использует общий `seen_cpe` по CPE, хотя один продукт/версия может встретиться на разных IP/портах.

**Воздействие:** запрос CVE/находка может быть сформирован только для первого соответствующего актива; отчёт недопоказывает затронутые адреса или доказательства.

**Рекомендация:** дедуплицировать запрос к NVD отдельно от списка asset associations; после одного lookup разнести CVE по всем найденным объектам.

### P3-05. Несколько источников CVE обобщаются слишком широко

**Доказательство:** `asm/cve.py:103-121,169,176-190` использует `criteria.startswith(prefix)`, неизвестная версия трактуется как потенциально подходящая; curated-правило Drupalgeddon2 применяет диапазон слишком широко для Drupal 7.x. `asm/facts.py:226-288,380-403` не воспроизводит полную вложенную AND/OR-структуру NVD configurations.

**Воздействие:** false positives и смешение «похоже по продукту» с «версия доказанно затронута»; оператору приходится вручную перепроверять много ложных находок.

**Рекомендация:** реализовать сравнение CPE и version ranges по правилам NVD, сохранять `unknown/unverified`, корректно разбирать AND/OR children, добавить граничные тестовые фикстуры.

### P3-06. Небольшие, но систематические пробелы качества

- `asm/scan.py:118` передаёт `sensitive=locals().get("sensitive", ())`, хотя переменная в этом scope не формируется; secret-scan путь для найденных открытых файлов остаётся пустым.
- `asm/cve.py` кэширует пустые/ошибочные ответы на длительный срок; синхронизация rate-limit между потоками ограничена. При сбое источник может выглядеть как достоверное отсутствие данных.
- `asm/score.py:184-208` позволяет реестру `low/internal` понизить приоритет; если registry неверен/устарел, высокий риск уходит вниз. Сохранять исходный технический severity независимо от бизнес-приоритета.
- `asm/report.py:216-228` и UI не всегда отделяют «данных нет/стадия не запускалась» от «проверено и чисто»; нужен явный статус coverage.

**Рекомендация:** различать `clean`, `not checked`, `failed` и `unknown`; не превращать отсутствие результата/неполный coverage в отрицательное заключение.

## Проверка конкретно `bin/llm-probe.py:110-190`

Короткий ответ: **да, скрипт умеет читать `~/.asm-cloud.sh`, но он его не `source`-ит и не исполняет.** `load_env()` сначала берёт `ASM_LLM_BASE/KEY/MODEL` из окружения; если заданы все три — файл не читает. Иначе разбирает его как простой текст по одной строке `export NAME=value` или `NAME=value`. Это безопаснее, чем выполнять произвольный shell-файл, но не поддерживает произвольный синтаксис `.sh`.

Важно для секрета: `build_request()` помещает key в HTTP-заголовок, а `call()` отправляет запрос обычным `urlopen()`. Следовательно, удалённый `http://` endpoint опасен для ключа; локальный loopback может быть допустим для локальной модели. В этих пробах сами prompt-ы синтетические (`llm-probe.py:57-66`), и код не вытаскивает находки из БД.

## Кандидаты, которые **не** засчитаны как подтверждённые

- `collect.crtsh_subdomains()` использует слабый на вид суффиксный фильтр, но последующая нормализация `asm/sources.py:166-179,204-205,329-351` проверяет границу DNS-метки. Не заявляю это как отдельный дефект.
- Потенциальный сбой `_pretty_cpe()` на malformed CPE не засчитан: статически достижимость именно некорректного входа не подтверждена.
- XSS, SSRF, гонки, уничтожение БД и поведение установщика не воспроизводились динамически; findings подтверждены по статическому пути данных/вызовов, не по факту эксплуатации.

## Порядок исправления

1. Закрыть сетевой управляющий API по умолчанию; добавить auth/TLS и лимиты HTTP-тел.

6. Исправить передачу реальных данных в облачные тесты и секреты в CLI/audit; разделить проверенные отрицательные результаты и неполное покрытие.
