# Векторная память — baseline этапа 3.1

**Дата:** 05.10.2026  
**Исходники поиска:** `asm/vector.py` не менялись. Добавлен только benchmark и усилены characterization-тесты ранжирования.

## Результаты

Linux sandbox, Python 3.13.14, SQLite 3.46.1. Для каждого размера — отдельный subprocess и временная SQLite-БД. Один прогрев + 3 измеренных вызова; p50 — медиана, p95 — nearest-rank. RSS — разница process high-water mark до/после измеряемых путей.

| Findings | `search_all()` p50 / p95 | `notes_for_scan()` p50 / p95 | RSS peak delta | SQLite-файл |
|---:|---:|---:|---:|---:|
| 1,000 | 40.797 / 41.075 ms | 525.009 / 563.352 ms | 5.20 MiB | 0.70 MiB |
| 10,000 | 416.246 / 425.372 ms | 4,632.314 / 4,842.147 ms | 46.50 MiB | 4.91 MiB |
| 100,000 | 4,335.874 / 4,796.243 ms | 48,347.058 / 48,467.306 ms | 486.66 MiB | 47.84 MiB |

RSS peak delta в таблице измерен по всему набору в каждом worker-процессе: после подготовки БД снимается baseline, затем выполняются `search_all()` и `notes_for_scan()`, после чего снимается high-water mark. Это **совместный peak двух путей**, не отдельная атрибуция пика к одной функции.

Профиль вызовов на один `search_all()`:

- `_all_findings()` вызывается один раз и материализует все N находок;
- `_vectors_cached()` вызывается один раз;
- `_read_stored()` вызывается дважды и суммарно декодирует **2N** строк векторного индекса.

Профиль одного `notes_for_scan(limit=4)` при этой фикстуре:

- `similar()` → `search_all()` выполняется 4 раза;
- каждый `search_all()` заново читает все N findings, хотя затем исключает текущий scan;
- `_vectors_cached()` вызывается 4 раза, `_read_stored()` — 8 раз, суммарно декодируется **8N** векторных строк; при 100k это 800,000 декодирований. Для scoring остаётся около 99% корпуса после исключения одного scan.

В этих размерах время обоих путей растёт примерно пропорционально числу findings. На 100k `notes_for_scan()` занимает около **48.3 s** — примерно **11.2×** одного прямого `search_all()` в этой фикстуре, хотя выполняет четыре вложенных поисковых прохода; запросы из текста отдельных findings длиннее тестового прямого запроса. Совместный прогон двух путей достигает RSS high-water delta примерно **487 MiB** даже при компактном тестовом векторе (какой отдельный путь задаёт максимум, этот замер не различает).

## Воспроизводимость и ограничения

- Скрипт: `benchmarks/benchmark_vector_paths.py`; сырые результаты и упорядоченные сигнатуры: `benchmarks/results/vector-path-baseline.json`.
- Только synthetic `.bench.invalid` данные; no network, scanner, local model, sqlite-vec extension, customer data or production DB.
- `ASM_DB` принудительно заменяется до импорта `asm`; каждый размер выполняется в собственном временном каталоге/процессе. Контрольный inherited sentinel SQLite-файл после полного прогона сохранил тот же SHA-256; временные benchmark-каталоги удалены.
- Установлен детерминированный fallback embedding размерности **16**: он позволяет безопасно измерить 100k в sandbox. RSS **не** характеризует реальную модель или штатную размерность 384; не экстраполировать его как production memory.
- Три измерения недостаточны для статистически надёжного tail latency; p95 nearest-rank в этом прогоне — максимум из трёх наблюдений. Это baseline относительного сравнения, а не SLO/Windows/production гарантия.
