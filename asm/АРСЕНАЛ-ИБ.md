# Арсенал: всё лучшее бесплатное из мира ИБ — как это встроено

Документ отвечает на один вопрос: **что именно из лучших бесплатных инструментов ИБ
работает внутри продукта, на каком шаге, что даёт заказчику и как этим управлять.**

Ни одного платного ключа, ни одной регистрации, ни прав root. Всё ставится одним
скриптом `bash bin/install-tools.sh` (при повторном запуске — только недостающее):
`--fast` — только ядро за ~1,5 минуты, `--force` — перекачать всё, `--tools` — без словарей.

**Где это лежит.** Каталог арсенала — `<проект>/build/tools`. Внутри проекта, потому что
каталоги вне его окружение стирает между сессиями; под именем `build`, потому что такие
каталоги не попадают в снимок workspace — иначе 13 742 шаблона и правила Semgrep раздувают
его до 914 МБ при лимите 128 МБ. Служебные кэши движков (ProjectDiscovery, nuclei, Wapiti)
и модуль perl `XML::Writer` тоже живут здесь, а не в домашнем каталоге.

Плюс данные: словари SecLists (110 000 / 20 000 поддоменов; 4 752 / 43 007 каталогов),
13 742 шаблона nuclei и ~4 000 правил Semgrep (бесплатный набор сообщества, лежит локально).

**Почему именно эти.** Отбор шёл по трём критериям: (1) инструмент — эталон в своей области,
(2) полностью бесплатен и работает без регистрации и ключей, (3) работает без прав root и не
ломает проверяемый сервис. Поэтому в арсенале нет эксплуататоров (metasploit, sqlmap) и
переборщиков паролей — это осознанная граница продукта, а не техническое ограничение.

## 2. Где каждый работает в конвейере

```
1  Разведка имён      subfinder + 11 источников без ключей + словарь типовых имён
2  DNS                dnsx (быстро) → встроенное разрешение (запасной путь)
3  Обогащение IP      RIPEstat, InternetDB (+ nmap-версии по найденным портам)
3б версии сервисов    nmap -sV  → продукт, версия, CPE  → цепочка в NVD
4  Веб-проба          httpx (статус, технологии, CDN) + встроенная проба по непокрытым
5  Идентификация      заголовки/баннеры/технологии → CPE
6  Проверки           tlsx (сертификаты), katana+gau (адреса), Nikto (веб-сервер),
                      Wapiti (веб-приложение), testssl (TLS)
6к Код и материалы   gitleaks + TruffleHog (секреты), Semgrep (опасный код),
                      trivy + OSV-Scanner (зависимости), trivy config (Dockerfile/k8s/terraform)
7  Активные           naabu (порты) + nuclei (шаблоны), ffuf — только по флагу
8  Уязвимости         CPE → NVD + CISA KEV + EPSS
9  Приоритеты/отчёт   скоринг, план закрытия, ИИ-разбор
10 Изменения          сравнение с прошлым анализом
```

## 3. Что добавлено 04.10 (второй заход по арсеналу)

- **nmap -sV** (этап 3б): точные версии сервисов и CPE. Раньше версия угадывалась
  по заголовкам, теперь подтверждается баннером. Проверено вживую: 4 сервиса у `45.33.32.156`
  (ssh, http, ntp, «Elite»).
- **Nikto** (этап 6): 26 замечаний по веб-серверу за один проход. Инъекционные проверки
  выключены навсегда (`-Tuning b2`): продукт не ищет уязвимости эксплуатацией.
- **testssl.sh** (этап 6): аудит TLS-конфигурации; служебные строки сканера отбрасываются,
  из результата берутся только значимые (протоколы, шифры, заголовки, сертификат).
- **gitleaks + trivy** (этап 6) для **материалов заказчика**: копия git-репозитория (только
  чтение), каталог с кодом или образ контейнера. Проверено вживую на публичном демо-проекте
  и образе `nginx:1.18`: 3 секрета в коде, 80 уязвимых библиотек в коде, 369 — в образе,
  у каждой — «обновить до какой версии».
- **Секреты в открытых файлах**: адреса с признаками `.env`, `.git/config`, бэкапов и т.п.
  теперь читаются (до 6 адресов, до 64 КБ) и проверяются gitleaks. Найденный секрет
  попадает в отчёт как **P0** с маскированной выдержкой (`AKIA…9T (20 символов)`) —
  доказательство есть, сам секрет в базу не копируется.
- **Защита от недостоверных результатов**: если сканер портов показывает «открыто всё»
  (прозрачный прокси или NAT в канале), результат отбрасывается с объяснением в журнале,
  а не превращается в сотни ложных находок.
- **Версии инструментов** показываются честно (`trivy v0.75.0`, `nikto v2.6.1`,
  `nmap v7.99`), а не «есть».

## 3б. Что добавлено вторым заходом (19 инструментов)

- **TruffleHog** — второй, независимый поиск секретов (другие детекторы и правила, чем у
  gitleaks, поэтому находки не дублируются). Проверка «живой ли ключ» **выключена по умолчанию**:
  она отправляет найденный ключ сервису-владельцу. Включается осознанно: `ASM_TRUFFLEHOG_VERIFY=1`.
- **Semgrep** — анализ исходного кода: `eval`, конкатенация в исполняемый код, слабая криптография,
  небезопасные сравнения и т.п. Правила — локальная копия бесплатного набора сообщества
  (интернет при проверке не нужен). На демо-проекте: **27 находок за 45 с**.
- **OSV-Scanner** — уязвимые зависимости по базе OSV.dev: на демо-проекте **314 находок за 3 с**,
  у каждой — версия, до которой надо обновиться. Работает независимо от trivy: две базы лучше,
  чем одна, а расхождения видны сразу.
- **trivy config** — ошибки конфигурации развёртывания (Dockerfile, kubernetes, terraform):
  контейнер под root, отсутствие лимитов, открытые порты и т.п.
- **Wapiti** — проверки веб-приложения. Список модулей задан жёстко и подобран так, чтобы
  ничего не ломать и не подбирать пароли: `backup, cms, htp, methods, wapp, wp_enum`.
  Инъекционные модули (sql, xss, exec, xxe, shellshock, crlf) не запускаются. Два модуля убраны
  осознанно: `nikto` — потому что ту же работу делает отдельный этап Nikto (иначе время аудита
  удваивается впустую), `takeover` — потому что на внешних адресах он «залипает» на DNS-запросах
  (свыше 3,5 минут без результата), а проверку захвата поддоменов и так делают шаблоны nuclei.
  Живой прогон (03.10): **75 замечаний за 7 секунд**, среди них — определение веб-сервера
  (`Apache HTTP Server 2.4.7`) и список CVE именно к этой версии. То есть Wapiti у нас работает
  вторым независимым источником CVE для веб-серверов, помимо версий из `nmap -sV`.
  Запуск Wapiti — трёх подводных камней избегаем явно: у него **нет** ключа `-q` (с ним он
  молча выходит без отчёта — выглядит как «ноль находок»), ключ `--scope domain` гонит обход
  всего домена и не укладывается ни в один лимит, а заранее созданный пустой файл отчёта
  мешает ему записать результат. Рабочая форма — без `-q`, без `--scope`, файл отчёта не
  создавать заранее, жёсткий предел `min(timeout, max_time+120)`.
  Чтобы самый долгий этап не растягивал аудит, **Nikto и Wapiti идут одновременно** (общий
  пул потоков) — на живом скане это экономит около двух минут.
- **Исправлена важная ошибка**: `nmap_services` вызывался без `-sV`, поэтому продукт и версия
  сервиса оставались пустыми — версии угадывались по заголовкам. Теперь эталонный движок
  даёт их точно (`OpenSSH 6.6.1p1`, `Apache httpd 2.4.7`) и CPE сразу уходит в NVD.
- **Разделены библиотеки резолвера**: приватные `.so` для `dig` лежат в `lib-dns`, потому что
  общий `LD_LIBRARY_PATH` подменял системные библиотеки и ломал Semgrep. Теперь `LD_LIBRARY_PATH`
  содержит только `libpcap` (нужен nmap и naabu).

## 5. Материалы заказчика (код, репозиторий, образ)

Панель → цель → «Материалы заказчика для внутренней проверки»: ссылка на репозиторий,
каталог с кодом, имя образа контейнера. Материалы сохраняются у цели и подставляются
в каждый следующий анализ автоматически. То же из командной строки:

```bash
python3 app.py scan client-site.ru --repo https://github.com/client/site.git
python3 app.py scan client-site.ru --code /home/audit/client-site
python3 app.py scan client-site.ru --image registry.client.ru/site:2.3
```

Копия репозитория делается только на чтение и удаляется после проверки; на стороне
заказчика ничего не меняется.

## 6. Черновики проверок nuclei (замыкание цикла)

`python3 app.py drafts <scan_id>` или кнопка «Черновики Nuclei» в панели находок:

- по находке с адресом собирается **заготовка шаблона** (id, severity, matcher по тому,
  что реально видели) — проверяется `nuclei -validate` (в наших прогонах — «All templates
  validated successfully»);
- по находке, снятой шаблоном nuclei, — **готовая команда повторной проверки** тем же шаблоном;
- ссылки на чужие ресурсы (NVD, MITRE и т.п.) целью проверки **не становятся**: адрес
  должен принадлежать проверяемому активу.

Замысел простой: после починки заказчик запускает те же проверки и видит, что находка
действительно закрыта.

## 7. Поиск по смыслу (локально, без интернета)

`asm/vector.py`: векторы находок лежат в SQLite (расширение `sqlite-vec`, косинусная метрика),
модель — локальная ONNX (`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`,
384 измерения, ~220 МБ). Если модели нет — работает встроенная векторизация n-грамм
(без зависимостей), и интерфейс честно пишет, какой режим включён.

```bash
python3 app.py search 19 "старое шифрование в ssh"
curl 'http://localhost:8000/api/scan/19/semantic?q=открытый каталог'
curl http://localhost:8000/api/vector          # состояние: расширение, модель, сколько проиндексировано
```

## 9. Правило безопасности

Активные проверки — только по письменному разрешению владельца (основание хранится у цели
и попадает в отчёт). Эксплуатации уязвимостей нет, перебора паролей нет, проверок «на отказ
в обслуживании» нет — и не будет: это не ограничение возможностей, а то, что делает аудит
аудитом, а не атакой.
