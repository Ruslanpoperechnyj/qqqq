# Проба Qwen3-Coder-Next — порядок запуска

Коротко: это **пробник «по приколу»**, а не замена рабочего движка. Боевая Gemma 4 12B
остаётся как есть (`build\llm\serve.cmd`, порт 8080, 60–86 ток/с). Coder-Next ставится
рядом, на свой порт **8081**, в ту же папку `build\llm` (модели — в `build\llm\models`,
пусковой файл — `build\llm\serve-coder.cmd`). Ничего общего с Gemma не пересекается.

Зачем вообще: посмотреть, что даёт 80-миллиардная MoE-модель на нашем железе, и судить
её **нашим конвейером**, а не рассказами из интернета. ИБ-бенчмарков в карточке модели
нет — «божественная для ИБ» это реклама.

---

## 1. Сначала — решение: какой квант качать

| квант | размер | влезает в 12 ГБ VRAM + 32 ГБ RAM | вердикт |
|---|---|---|---|
| `UD-TQ1_0` | 18,9 ГБ | да, с запасом | запустится гарантированно; качество — «посмотреть» |
| **`UD-Q2_K_XL`** | **26,8 ГБ** | **впритык** | **по умолчанию: лучшее качество из реально влезающих** |
| `UD-Q3_K_S` | 33,3 ГБ | нет | Windows + KV-кеш добьют; диск начнёт молотить |
| `UD-Q3_K_M` / `UD-Q3_K_XL` | 35,9 / 36,3 ГБ | нет | то же |

Почему Q2_K_XL может пойти, хотя «не влезает»: модель разряженная (MoE) — на каждый
токен читается только ~3 млрд параметров из 80 млрд, а llama.cpp держит файл
отображённым в память, и в RAM живут только нужные страницы экспертов. Если Windows
начнёт вытеснять их на диск, скорость рухнет ниже 2 ток/с — это видно на первом же
замере (шаг 5), и тогда второй запуск делаем на `UD-TQ1_0`.

**Освободить до запуска:** закрыть браузер и всё лишнее (на 26,8 ГБ модели при 32 ГБ RAM
остаётся ~4–5 ГБ на Windows и служебные буферы), проверить, что видеопамять свободна
(`nvidia-smi` — чужого процесса быть не должно), и что на диске ~30 ГБ.

---

## 2. Шаги

**Шаг 0. Свежий движок (важно).** Нужен бинарь, который знает архитектуру `qwen3next`
и флаг `--n-cpu-moe`: их добавляли не сразу, а разбор вызовов инструментов для этой
модели llama.cpp правил в феврале 2026. Старый бинарь просто не поймёт модель.

```
powershell -ExecutionPolicy Bypass -File bin\install-llamacpp.ps1 -SkipModel
```

`-SkipModel` — чтобы Gemma не качалась заново; папка `build\llm\models` не чистится.
Если Gemma уже стоит и бинарь свежий (этой весны и позже) — шаг можно пропустить.

**Шаг 1. Место на диске.**

```
Get-PSDrive C | Select-Object Used,Free
```

**Шаг 2. Скачать модель и собрать пусковой файл.**

```
powershell -ExecutionPolicy Bypass -File bin\install-coder-next.ps1 -Quant UD-Q2_K_XL
```

Качает 26,8 ГБ в `build\llm\models\Qwen3-Coder-Next-UD-Q2_K_XL.gguf` и пишет
`build\llm\serve-coder.cmd`. Обрыв связи не страшен: повторный запуск продолжит с места.
Проверить движок без качания модели: тот же скрипт с `-SkipModel`.

**Шаг 3. Запуск.**

```
build\llm\serve-coder.cmd
```

Ждать в окне строку `server is listening on http://127.0.0.1:8081`. Первая загрузка
с диска может занять 1–3 минуты — это нормально, это не зависание.

**Шаг 4. Проверить, что живой.**

```
curl.exe http://127.0.0.1:8081/v1/models
```

Должна вернуться модель `qwen3-coder-next`.

**Шаг 5. Первый замер — 60 секунд, и сразу видно, влезло ли.**

Открыть в браузере `http://127.0.0.1:8081` — у llama-server есть свой чат. Спросить
что-нибудь, требующее ~100 токенов ответа. Смотреть в окне `serve-coder.cmd` строку
`llama_perf` → `eval time ... , N tokens per second`.

| что видно | что это значит |
|---|---|
| больше 12 ток/с | память работает лучше расчёта — скажите мне, это интересно |
| **измерено 06.10: 25,4 ток/с** — при ползунке экспертов = 40 и закрытых браузере/Discord; 9,6 было при 0 | так и получается; у Gemma на той же машине 60-86 |
| 3–10 ток/с | норма для машины без правильной раскладки, идём дальше |
| меньше 2 ток/с, и диск в Task Manager загружен на 100% | не влезло: `Ctrl+C` в окне, перезапуск скрипта с `-Quant UD-TQ1_0` |

Заодно глянуть `nvidia-smi`: занято должно быть примерно 6–9 ГБ видеопамяти.

**Шаг 6. Главное — прогон №2 (наша задача, а не бенчмарки).**

В чате `http://127.0.0.1:8081` вставить целиком содержимое `knowledge/prompts/hard-task.md`
(13,5 КБ, задача самодостаточная) и попросить то, что просит сам файл. Ответ сохранить как
`knowledge/prompts/hard-task-answer-coder.md` — либо просто бросьте текст в чат, сохраню сам.

**Шаг 7. Проверка ответа нашим конвейером.**

```
python3 app.py --set ASM_DB=data/hard-task.sqlite --set ASM_SCOPE=10.20.4.0/24 agent check 1 --file knowledge/prompts/hard-task-answer-coder.md
```

Стенд уже собран и лежит в рабочей копии: `data/hard-task.sqlite` (цель, скан 22-дневной
давности, кэш NVD/KEV/EPSS по двум версиям). Если файл потеряется —
`python3 tools/seed-hard.py` соберёт заново.

Сравнивать будем с прогоном №1 на Gemma: **поймано 4 ловушки из 8**, ошибка на
CVE-2026-2044 (модель считала неприменимую уязвимость применимой). Тот же ответ,
прогнанный сейчас, даёт ровно те же строки — база сверена.

**Шаг 8. Скорость на наших задачах (по желанию).**

```
python3 bin/llm-bench.py --set ASM_LLM_BASE=http://127.0.0.1:8081/v1 --set ASM_LLM_MODEL=qwen3-coder-next --pro --repeat 2
```

**Шаг 9. Остановить.**

`Ctrl+C` в окне `serve-coder.cmd`. Gemma не тронута: `serve.cmd` запускается как обычно
и работает на 8080. Две модели одновременно не поднимать — они не влезут в память вместе.

## 3. Чего ждать по качеству (чтобы не обмануться)

* Модель **«не думающая»**: отдельного блока рассуждений не выдаёт, отвечает сразу.
  Для скорости это плюс, для планирования — минус: сложную задачу она не «пережуёт»
  перед ответом.
* 80 млрд звучит грозно, но на 2 битах это уже сильно побитая модель. Честный ориентир:
  Gemma 4 12B у нас в Q4 — «целая», эта — сжата в 6–10 раз сильнее. Ждать, что она
  «порвёт» Gemma на планировании, оснований нет; проверим — узнаем.
* Кодовый фокус (SWE-bench ~70 %, Terminal-Bench ~52 %) — это про написание кода,
  а не про ИБ-планирование.

## 4. Если что-то пошло не так

| сообщение | причина | что делать |
|---|---|---|
| `unknown model architecture: qwen3next` | старый бинарь | шаг 0 |
| `unknown argument: --n-cpu-moe` | бинарь старше февраля 2026 | шаг 0; крайний случай — заменить в `serve-coder.cmd` на `--cpu-moe`, а `-ngl 99` на `-ngl 20` |
| `failed to allocate` при загрузке | мало RAM | квант `UD-TQ1_0` |
| диск 100 %, скорость < 1 ток/с | модель вытесняется в файл подкачки | квант `UD-TQ1_0` |
| ответ обрывается на полуслове | контекст 32K + длинный ответ | разбить вопрос на части |

## 5. Что прислать в чат по итогу

1. строку `llama_perf` (скорость генерации);
2. ответ модели (файлом или текстом);
3. что показывали `nvidia-smi` и Task Manager по памяти в момент работы.

Этого хватит, чтобы (а) честно сказать, стоит ли связка «карта + большая модель» возни,
и (б) сравнить с прогоном №1 цифрами, а не впечатлением.

## Приложение: то же самое в LM Studio (если не хочется команд PowerShell)

LM Studio удобнее для «по приколу»: качает сам, настройки мышкой. Ограничение одно и
важное: у него **один тумблер** «эксперты на CPU» (все эксперты сразу), а в llama.cpp
можно отдать только часть (`--n-cpu-moe 40`) — поэтому LM Studio обычно медленнее
нашей `serve-coder.cmd`. Сравнивать скорость честно в одном месте, а не «вроде тормозит».

**Подготовка.**
1. Обновиться: `Settings → About/Update`. Нужен свежий билд — архитектура `qwen3next`
   появилась не сразу; если LM Studio ругается `unknown architecture` — дело в этом.
2. `Settings → Runtime → llama.cpp` — выбрать самый свежий рантайм (кнопка загрузки нового).
3. Включить `Settings → Developer` (в режиме разработчика видны «Advanced Settings» при загрузке).
4. Модель: поиск по `Qwen3-Coder-Next`. Если нужного кванта (UD-Q2_K_XL) в поиске нет
   — качаем нашим скриптом (-SkipModel не нужен) и в LM Studio тянем файл в окно
   `My Models` (или ставим `build\llm\models` дополнительной папкой моделей).

**Настройки загрузки (правый боковой столбец, «Advanced»):**

| настройка | значение | почему |
|---|---|---|
| Context Length | **32768** | 12 ГБ не резиновые; больше — только в ущерб скорости |
| Force Model Expert Weights onto CPU — **только в LM Studio 0.3.x** | ВКЛ | без этого 26,8 ГБ весов не влезут: эксперты уходят в RAM, на GPU остаётся внимание |
| Number of layers for which to force MoE expert weights onto CPU — **в 0.4.x вместо тумблера** | **40** (не 0!) | это аналог `--n-cpu-moe`: сколько слоёв держат экспертов в RAM. 0 = ни одного → 26,8 ГБ в 12 ГБ не влезают |
| GPU Offload | **Max** (оценка VRAM должна быть ≤ 10,5 ГБ; иначе снизить до ~40 слоёв) | внимание и эмбеддинги считаются быстро только на GPU |
| Flash Attention | **ВКЛ** | скорость и меньше памяти |
| K/V Cache Quantization | **Q8_0** | экономия памяти под кеш |
| Offload KV cache to GPU | **ВКЛ** | кеш у этой модели маленький (гибридное внимание), место есть |
| CPU Threads | **6** | у 7500F шесть физических ядер |
| Keep model in memory | ВКЛ | для пробы удобно |
| Unload previous model | ВКЛ | иначе Gemma останется в памяти и они вдвоём не влезут |

**Параметры сэмплинга (там же, ниже):** temperature **1.0**, top-p **0.95**, top-k **40**,
min-p **0.01**, repeat/presence penalty — **выключить** (1.0). Это рекомендация Qwen;
в LM Studio штраф повтора по умолчанию 1.1 — для этой модели он вреден.

**Сохранить как настройки по умолчанию для модели:** `My Models → шестерёнка у карточки`
→ параметры загрузки. Иначе при следующем запуске подхватятся настройки Gemma, и наоборот.

**Если надо проверить нашими командами** — в чате LM Studio задачу даём как обычно,
а адрес для замеров другой: `--set ASM_LLM_BASE=http://127.0.0.1:1234/v1`.

**Признак, что дело в тумблере:** LM Studio даёт заметно меньше токенов, чем
`serve-coder.cmd` на том же кванте — это плата за «все эксперты на CPU» вместо части.
Выбирать по вкусу; на качество разницы нет.
