# ASM — свой аналог «CVE.Global» для небольших заказов

Рабочий прототип платформы анализа внешнего периметра (EASM), повторяющий функции
инструмента из видео «ВЕСЬ МИР УЖЕ ВЗЛОМАН». Написан на чистом Python 3 — без зависимостей,
без Docker, без платных API.

```
python3 app.py serve          # дашборд на http://localhost:8000
```

Прототип уже проверен на реальном хосте: собирает поддомены, открытые порты, технологии,
сопоставляет версии с NVD, приоритизирует по CVSS × EPSS × CISA KEV и формирует отчёт
для заказчика с указанием основания работ.

---

## 1. Что именно делают в видео и что сделано здесь

| В видео | Как это устроено внутри | В этом прототипе |
|---|---|---|

| «Анализ инфраструктуры за 7 секунд» | Предрасчёт + кэш + корреляция справочников | `scan.py` + SQLite-кэш: повторный анализ того же объекта идёт мгновенно |
| «На IP — CVE 2023 года, подключение не защищено» | Баннер/версия → CPE → сопоставление с NVD | `identify.py` → `cve.py` (точный запрос NVD по CPE версии) |
| «Предиктор анализирует, каким действиям инфраструктура подвержена» | Скоринг по CVSS/EPSS/KEV + экспозиция | `score.py`: объяснимая формула с P0–P3 |
| «ИИ объясняет простыми словами, приоритет защиты, сценарий атаки» | LLM поверх структурированных данных | `ai.py`: оффлайн-режим (шаблоны+правила) и LLM-режим (любой OpenAI-совместимый эндпоинт) |
| «Инфраструктурный профиль, карта связей» | Граф домен→IP→ASN→сервис→технология | `store.py` (edges) + граф в дашборде (SVG, силовая укладка) |
| «Слепок человека по цифровым следам» | OSINT по людям | **Сознательно не реализовано** — это уже не аудит периметра, а обработка ПДн (152-ФЗ) |

## 2. Быстрый старт

> **Windows:** команды ниже — для Git Bash. Что именно там отличается
> (переменные окружения, `.exe`, установщик nmap, остановка процессов) —
> раздел 13 в конце документа.

```bash
# 0. Один раз: бесплатный арсенал ИБ (19 инструментов). Полная установка ~4 минуты.
bash bin/install-tools.sh
bash bin/install-tools.sh --fast          # только ядро (разведка, порты, проверки) — ~1,5 минуты
python3 app.py engines                    # что установлено, какая версия, чем что закрывается

# Инструменты внутренней работы ставятся тем же установщиком и ложатся в два
# разных каталога, и различие важное:
#   build/tools/bin/       — запускается с этой машины (chisel, ligolo-proxy, kerbrute)
#   build/tools/payloads/  — переносится НА цель (linpeas, winPEAS, pspy, SharpHound,
#                            ligolo-agent). Это файлы в файловой системе заказчика,
#                            и их список нужен для уборки после работ.
# Часть инструментов ставится не автоматически, и это осознанно: hashcat
# публикуется одним .7z со всем каталогом (один бинарник не работает),
# BloodHound CE вообще без архивов — только контейнеры. Подробности — раздел 19
# плана.
bash bin/install-tools.sh --selftest --only=chisel,linpeas.sh,SharpHound.exe

# 1. Дашборд
python3 app.py serve                      # http://localhost:8000

# 2. Через CLI
python3 app.py add client.ru --client "ООО «Ромашка»" --ref "Договор №14-А от 12.05.2026"
python3 app.py scan client.ru             # полный анализ: 10 этапов, ждёт завершения
python3 app.py scan client.ru --no-wait   # то же, но в отдельном фоновом процессе
python3 app.py scan 2                     # по номеру цели (число — это всегда ID ЦЕЛИ, не скана)
python3 app.py findings 1                 # находки P0/P1
python3 app.py report 1 --out client.md   # отчёт заказчику
python3 app.py list                       # цели и анализы
python3 app.py engines                    # арсенал: 19 инструментов, версии, шаблоны, словари
python3 app.py drafts 19                  # черновики проверок nuclei по находкам анализа
python3 app.py search 19 "старое шифрование"   # поиск по находкам по смыслу (локальная модель)
python3 app.py log 19                     # журнал анализа: что запускалось, что пропущено и почему
python3 app.py log 19 --only пропущен     # только строки с подстрокой
python3 app.py verify 19                  # перепроверить: какие порты ещё открыты
python3 app.py verify 19 --mark-fixed     # ...и пометить закрытыми те, что не воспроизвелись
```

Настройки. Их больше сотни, и в PowerShell нельзя написать `ASM_КЛЮЧ=значение команда`,
поэтому любую можно задать одной строкой — прямо перед командой:

```bash
python3 app.py handover access 1 --account 'DOMAIN\svc_adm' \
               --privilege 'администратор домена' --method 'WinRM 5985' \
               --target-host dc01 --verify 'winrs … whoami /groups'
python3 app.py handover placed 1 --file linpeas.sh --where-host srv-01 --path /tmp/.cache-upd
python3 app.py handover removed 1 --id 3      # отметить убранным
python3 app.py handover show 1                # документ + проверка готовности
python3 app.py handover write 1 --out передача.md
python3 app.py stealth                        # чем выходим наружу и чем выглядим
python3 app.py stealth check                  # проверить выход запросом, а не настройкой
python3 app.py memory "открытый каталог"        # что похожего было на других объектах
python3 app.py memory --finding 42              # чем эта находка похожа на прошлые
python3 app.py memory --index                   # пересобрать индекс по всем анализам
python3 app.py --settings                       # все настройки и их текущие значения
python3 app.py --set ASM_PROFILE=pentest scan client.ru
python3 app.py --set ASM_NMAP_TOP=1000 --set ASM_WORKERS=4 scan client.ru
```

`--set` разбирается до импорта модулей — иначе настройки, которые читаются один раз
при старте, были бы молча проигнорированы. Ключи вне пространства `ASM_` отклоняются.

Агент (предлагает шаги, ничего не делает без подтверждения):

```bash
python3 app.py agent start client.ru --operator Иванов --deadline 2026-12-31T18:00:00+00:00
python3 app.py agent plan 1               # что предложено и ждёт решения
python3 app.py agent extend 1 --scan 19   # предложить шаги по плейбукам, подходящим к анализу
python3 app.py agent approve 3 --operator Иванов
python3 app.py agent stop 1 --operator Иванов   # одно нажатие: убить процессы, закрыть сессию
python3 app.py agent resume               # снять флаг остановки (сессию не воскрешает)
python3 app.py agent selftest             # проверить кнопку СТОП на этой машине
```

Пакет передачи доступа. Работа заканчивается не отчётом, а демонстрацией, и
документ, который её сопровождает, остаётся у заказчика. Секрета в нём нет и
быть не может: `handover access` его не спрашивает, а в схеме базы нет колонки,
куда его можно было бы положить — это гарантия сильнее обещания. Свободный
текст проверяется на похожее на секрет и **отклоняется**, а не помечается
предупреждением: NT-хеши, выгрузки из базы домена, ключи, токены.

Цепочка шагов со временем берётся из журнала, а не набирается руками — иначе
она ничего не подтверждает. Границы работ перечисляются явно, включая
отклонённые шаги. Остановленные работы не выдаются за оконченные.

Незакрытая уборка не даёт пакету считаться готовым: `handover show` вернёт 1,
пока перенесённый файл числится на объекте. `SharpHound.exe` в `C:\Windows\Temp`
ищут при разборе и находят.

Внутренние шаги (после входа на хост) стоят отдельно от наружных и никогда не
предлагаются сами. По вашему решению от 06.10.2026 агент **сам отправляет**
команды одобренного шага на хост (SSH для Linux, PowerShell Remoting для
Windows) и приносит вывод — соединение всегда открываем мы, туннелей и обратных
соединений нет:

```bash
python3 app.py agent inside                    # список внутренних шагов
python3 app.py agent inside inside_privileges 1 \
               --inside-host srv-01 --inside-os linux --inside-user www-data
python3 app.py agent plan 1                    # что агент подготовил
python3 app.py agent approve 5 --operator Руслан
python3 app.py agent run 1                     # выдать команды (не выполнять!)
python3 app.py agent step 5                    # перечитать команды шага позже
```

`agent run` принимает **номер сессии**, а не номер шага: он проходит по всем
одобренным шагам сессии и **сам отправляет** команды внутрь (пароль доступа —
скрытым вводом: `--secret-prompt`, либо `ASM_INWARD_SECRET`; на диск и в журнал
он не попадает). Если транспорта нет или он выключен (`ASM_INWARD=off`), шаг
по-прежнему выдаёт точные команды для ручного запуска — и говорит, почему. В выдаче внутреннего шага всегда три части: перенос
файла под безликим именем, запуск и **уборка** — с готовыми командами отметки
`handover placed` и `handover removed`.

Команды берутся от модели, если она подключена (каждая проверена воротами
поимённо), и тогда `agent plan` показывает их **до** одобрения. Без модели
команды готовятся правилами, и текст шага говорит об этом прямо — с причиной.

То же самое есть в дашборде: кнопка **🤖 Шаги агента** в шапке. Там видно план
сессии, описание каждого шага, его класс и статус; оттуда шаг одобряется,
отклоняется и выполняется. Одобрение остаётся решением человека и так же
пишется в журнал аудита — панель не ослабляет ворота, а убирает переключение в
терминал, из-за которого начинают одобрять пачкой, не читая. Что через панель
нельзя: одобрить шаг повторно (отказ называет причину), выполнить неодобренный
шаг, выполнить что-либо после нажатия СТОП.

Правила, вшитые в код:

- **Шаг, кладущий файл, всегда `impact`** — при любом профиле. Профиль снимает
  ограничения на проверки, но не делает необратимое обратимым.
- **Один хост — одно одобрение.** `inside_next_host` со списком хостов
  отклоняется ещё при постановке, а не при выполнении.
- **Без записанного доступа шаг с файлом не ставится.** Пока доступ не записан,
  пакет передачи собрать нельзя, а файл на хосте уже появится.
- **Система хоста называется явно** (`--inside-os`): от неё зависит, какой файл
  класть. Файла под эту систему может не быть вовсе (`pspy64` — только Linux), и
  тогда шаг не ставится, а не кладёт на хост неработающий файл.
- **Запуск, отметка и уборка — один и тот же путь.** Имя файла выбирает человек
  один раз; `%RANDOM%` в плане нет, потому что cmd раскрывает его заново при
  каждом вызове и уборка бьёт мимо.
- **Временных копий в плане нет** (`mktemp`, `%TEMP%\wp.tmp`): каждый файл,
  оказавшийся на хосте, должен быть в записи об уборке.


Скрытность. За связывание личности с работой по договору предусмотрен штраф,
поэтому всё, что выходит наружу, идёт через `asm/stealth.py` — одно место, а не
разбросанные по файлам строки. Два направления разведены намеренно: **на объект**
наш трафик увидят, и он должен выглядеть обычным визитом; **к внешним сервисам**
(crt.sh, InternetDB, NVD) запрос уходит с домашнего адреса, и именно эта пара
«адрес + домен заказчика» связывает личность с работой.

`require` запрещает прямой выход наружу: нет прокси — запрос не делается вовсе,
и причина записывается в отчёт. Пустой результат поиска выглядел бы как «ничего
не найдено», а это неотличимо от ошибки.

**Режим по умолчанию — `off`**, ничего не проверяется. Так обычная работа не
ломается из-за отсутствия прокси. Перед контрактом режим надо поднять осознанно:

```bash
python3 app.py --set ASM_STEALTH=require \
               --set ASM_PROXY_OUTWARD=http://адрес:порт \
               --set ASM_SOCKS=адрес:порт scan 19
```

`ASM_SOCKS` нужен отдельно: перебор портов идёт сырыми сокетами, и HTTP-прокси
его не берёт. Обычно это туннель на своём узле — `ssh -N -D 1080 user@vps`.

**VPN как прикрытие (без VPS и без карты).** Прокси инструмент видит и умеет им
пользоваться; системный VPN он видит иначе — трафик идёт мимо процесса, и
доказать работой, что туннель есть, нельзя. Поэтому есть третий признак:
`ASM_COVER=vpn` — «прикрытие вне процесса, подтверждено настройкой». Признак
считается поднятым, только если задана сама настройка **и** в системе виден
туннель (адаптер WireGuard/OpenVPN/Proton, устройство `tun*`):

```bash
python3 app.py --set ASM_STEALTH=require --set ASM_COVER=vpn scan 19
python3 app.py stealth cover     # туннель, фактический адрес выхода и резолвер DNS
```

`stealth cover` показывает три вещи, которые надо увидеть глазами: **адаптер**
туннеля, **адрес выхода** (запросом, извне) и **резолвер DNS**. Утечка DNS —
частая беда VPN: шифрованный трафик уходит через туннель, а имена доменов всё
равно спрашиваются у провайдера, и домен заказчика связывается с личностью.
Если резолвер — провайдерский, включите в VPN «использовать DNS VPN».

Скорость запросов к объекту — тоже часть скрытности и, что важнее,
безопасности чужого сервиса: 500 пакетов в секунду в состоянии положить
хрупкое оборудование. В щадящем профиле `safe` (он по умолчанию) скорости
ниже в разы: naabu 150, nuclei 25, httpx 20, katana 10, nmap 150, ffuf 40 против
500/80/60/30/500/120 в `pentest`. Значение колеблется на ±20 % от запуска к
запуску: ровный темп — такой же признак автоматизации, как одинаковый
User-Agent. Переопределяется настройкой (`ASM_NUCLEI_RATE`, `ASM_NMAP_RATE`,
`ASM_FFUF_RATE` и т. п.), `0` — без ограничения.
`stealth` показывает по каждому из 14 каналов, прикрыт он или нет, и не выдаёт
сырые пути за прикрытые.

Кнопка СТОП проверяется, а не предполагается. `agent selftest` запускает настоящее
дерево процессов и бьёт по нему той же функцией, что и кнопка, потом проверяет,
что не выжил никто. Итог — не «сигнал отправлен», а «процесс мёртв». Запускать
её нужно **на Windows**: путь `taskkill` отличается от пути POSIX, и правильность
одного ничего не говорит о другом.

После остановки команда показывает не только число убитых, но и тех, кто выжил.
Непустой список — это сигнал, что воздействие на объект продолжается.

База знаний:

Свои плейбуки кладутся в `knowledge/playbooks/*.yaml` — формат и все правила
проверки описаны в `knowledge/playbooks/README.md`. Проверка строгая намеренно:
опечатка в имени поля не падает, а молча не работает, и в аудите это выглядит
как «инструмент ничего не предложил». Посмотреть замечания — `app.py kb
playbooks` и `app.py kb status`.


```bash
python3 app.py kb status                  # что загрузилось, сколько уточнений, предупреждения
python3 app.py kb playbooks               # плейбуки: условия срабатывания и цепочки
python3 app.py kb match 19                # какие плейбуки подходят к результатам анализа
python3 app.py kb refine 42 --operator Иванов   # запомнить ложное срабатывание как уточнение
python3 app.py kb evidence impact         # что приложить к находке этого класса
python3 app.py kb learn 19 --dry-run      # что запомнится по ложным срабатываниям скана
python3 app.py kb learn 19 --operator Иванов   # запомнить
python3 app.py kb list                    # накопленные уточнения с номерами
python3 app.py kb forget 7                # убрать ошибочное
```

Отмечать ложные срабатывания отдельной командой не нужно: пометка «ложное срабатывание»
в веб-интерфейсе или в отчёте сама попадает в память. Отключается через
`--set ASM_AUTO_LEARN=0`.

Уточнение прячет находку во всех следующих аудитах, поэтому ошибочное стоит убирать
сразу — `kb list` показывает номер, `kb forget` убирает.

Память между объектами. `search` ищет внутри одного анализа, `memory` — по всем:
что похожего уже встречалось у других заказчиков и чем это кончилось (ложное
срабатывание, исправлено, принят риск). Работает локально, без интернета:
настоящая модель эмбеддингов, если установлена, иначе встроенная векторизация
n-грамм — она слабее по смыслу, но честно сообщает об этом в выводе.

`agent extend` показывает такие подсказки сам. Это подсказка, а не вердикт:
на другом объекте контекст другой.


Плейбуки лежат в `knowledge/playbooks/*.yaml` — их можно дописывать без правки кода.
Каждый шаг обязан существовать в каталоге агента; `handoff_access` в плейбуке
запрещён: получение доступа всегда решает оператор, не шаблон.

Материалы заказчика для внутренней проверки (код, репозиторий, образ контейнера):

```bash
python3 app.py scan client.ru --repo https://github.com/client/site.git
python3 app.py scan client.ru --code /home/audit/client-site
python3 app.py scan client.ru --image registry.client.ru/site:2.3
```

Полезные переменные окружения:

```bash
export NVD_API_KEY=...        # ускоряет обогащение CVE в 10 раз (бесплатный ключ на nvd.nist.gov)
export ASM_LLM_BASE=http://localhost:11434/v1   # Ollama / OpenAI / vLLM — для ИИ-собеседника

# Подключить модель и проверить это одной командой (пример — LM Studio):
python3 bin/llm-bench.py --models            # какие модели отдаёт сервер (имя для ASM_LLM_MODEL)

               --set ASM_LLM_MODEL=gemma4:12b-it-qat mode check   # строка «модель отвечает»

# необязательно: ASM_TG_TOKEN + ASM_TG_CHAT (или ASM_WEBHOOK_URL) — уведомления о завершении
export ASM_MAX_SUBDOMAINS=500 # лимиты глубины анализа
export ASM_ACTIVE_SCAN=0      # отключить активный этап (по умолчанию включён)
export ASM_ACTIVE_TIMEOUT=600 # предел времени на активные проверки, секунды
```

## 3. Конвейер: десять этапов

(Полный список шагов с привязкой к инструментам — `АРСЕНАЛ-ИБ.md`, раздел 2.)

```
1. Discover  CertSpotter → crt.sh — поддомены из логов выдачи сертификатов
            (объект не трогаем). Первым идёт CertSpotter: crt.sh отдаёт 502
            пачками, и когда он молчит, замена уже подставлена — источник
            считается отработавшим, а не «ничего не нашёл».
2. Resolve   DNS over HTTPS    — какие имена реально отвечают, в какие IP
3. Enrich    InternetDB+RIPE   — открытые порты, CPE-версии, CVE-имена, ASN/провайдер/страна
4. Probe     HTTP/TLS          — ОДИН запрос на веб-порт: заголовки, титул, сертификат
5. Identify  правила           — Server / X-Powered-By / meta generator / cookies / порты → продукт+версия
5b. Active   naabu + nuclei     — свои порты (не из чужих индексов) и проверки уязвимостей по шаблонам
6. CVE       NVD+KEV+EPSS      — CPE версии → ровно те CVE, что касаются этой версии
7. Score     формула           — приоритет P0..P3 с объяснением каждого множителя
8. Diff      сравнение         — что появилось/исчезло с прошлого анализа (мониторинг)
9. Report    правила или LLM   — резюме для руководителя, приоритет, сценарий, план на неделю
```

Важная деталь из этапа 3–4: **всё, что можно, берётся пассивно** (из публичных индексов),
и только по веб-портам делается по одному лёгкому запросу. Никакого перебора, никакой
эксплуатации. Это и есть разница между «анализом» и «сканированием», о которой говорит
автор видео: при сканировании вы стучитесь в объект, при анализе — читаете то, что объект
сам публикует для подключения.

### Активный этап (5b): когда «анализ» уже недостаточно

Публичные индексы знают не всё: закрытый периметр, свежие сервисы и внутренние адреса
там не видны. Поэтому по команде инструмент умеет **сам** пройти по согласованным адресам:

* **naabu** — сканирование портов (SYN, при нехватке прав — обычное соединение);
* **nuclei** — проверки по 13 000+ шаблонам (уязвимые версии, открытые служебные файлы,
  конфигурация, дефолтные учётные записи, захват поддоменов, технологии).

Встроенные ограничения — чтобы не навредить: исключены категории `dos`, `fuzz`, `intrusive`,
`brute-force`; перебор паролей и эксплуатация не выполняются; лимит скорости 80 запросов/с,
предел времени 600 с, не больше 12 адресов за один прогон. Отключается одной переменной
`ASM_ACTIVE_SCAN=0`. Кнопка «активные проверки» есть и в дашборде.

### Как закрыть: рекомендации к каждой находке

Инструмент не только находит проблему, но и объясняет, что делать. К **каждой** находке
прикладывается блок «Как закрыть»: класс проблемы, шаги по-русски, команды и куски конфигов
(Apache/nginx/SSH/MySQL/Redis/Docker/WordPress…), а также чем проверить результат.
В отчёте для заказчика из этого собирается сводный план на неделю, сгруппированный по типам работ.

## 5. Как считается «приоритет защиты»

```
база      = CVSS²            (9.8 → 96, 7.5 → 56, 5.9 → 35, 4.3 → 18)
экспозиция: TLS ×1.10 · HTTP ×1.15 · небанальный порт наружу ×1.20
EPSS:      ≥50% ×1.45 · ≥10% ×1.20 · ≥1% ×1.05
техдолг:   ≥5 лет ×1.12 · ≥2 лет ×1.06
score     = база × множители

Ни одного слагаемого: только произведение и потолок.

P0 ≥ 85 или CISA KEV (эксплуатация уже фиксируется)   — закрыть за 24–72 часа
P1 ≥ 55                                              — 1–2 недели
P2 ≥ 28                                              — плановое обновление
P3 <  28                                             — к сведению
```

Раньше техдолг прибавлялся к произведению (+4/+8), и это работало против
смысла: находка с базой 18 и возрастом 6 лет получала 26 — больше, чем находка
с базой 25 без долга. Причина слабая перевешивала актуальную проблему. Возраст —
такая же поправка, как экспозиция, и стоит в том же множителе.

Любое число в отчёте можно защитить перед заказчиком: в `rationale` расписано,
из чего сложилась оценка, и у каждого множителя есть источник (NVD / FIRST / CISA).
Именно это отличает инструмент от «ИИ предсказал уязвимость»: предсказание тут —
не магия, а прозрачный скоринг по публичным метрикам.

## 6. ИИ-слой: как это работает на самом деле

В видео ИИ «понимает» найденное и объясняет словами. Технически это две разные вещи:

1. **Оффлайн-режим** (по умолчанию, `ai.py`): из структурированных данных собираются
   «Резюме для руководителя», «Приоритет защиты», «Сценарий атаки», «План на неделю»
   по правилам и шаблонам. Работает без интернета и без ключей, результат детерминирован.
2. **LLM-режим**: тот же срез данных (JSON: находки, CVSS/EPSS/KEV, ASN, изменения) уходит
   в модель через OpenAI-совместимый API, и она пишет текст «для человека».

**Каким движком запускать модель.** Три пути, все бесплатные, разница — в
скорости и контроле:

| движок | адрес по умолчанию | кому |
|---|---|---|
| **llama.cpp (`llama-server`)** — боевой | `http://127.0.0.1:8080/v1` | наш случай: прямой движок, квантованный KV-кеш (`--cache-type-k/-v q8_0`, на 12 ГБ это 16K против 32K контекста), MTP-драфтер, все флаги. Ставится `bin/install-llamacpp.ps1` |
| LM Studio | `http://127.0.0.1:1234/v1` | быстрая личная проверка: GUI, скачивание модели в один клик. Внутри тот же llama.cpp |
| Ollama | `http://127.0.0.1:11434` | запасной: проще всего поставить, но медленнее на NVIDIA и без части флагов. `bin/install-llm.ps1` |

Стиль подключения определяется сам (`ASM_LLM_STYLE=auto`): `:11434` — Ollama,
всё остальное — OpenAI-совместимый. Так что достаточно задать адрес. Какие
модели сервер реально отдаёт — `python3 bin/llm-bench.py --models`.

Модель **не ищет** уязвимости — она объясняет то, что нашли инструменты. Если вы захотите
локальную модель без интернета: `ollama pull qwen2.5:14b` и `ASM_LLM_BASE=http://localhost:11434/v1`.

**Планировщик шагов: модель предлагает, код проверяет.** План цепочки может
строить локальная модель — но не командами, а выбором из готового каталога
действий (17 наружных и 6 внутренних). Ей дают подсказки: что уже нашли, какие
плейбуки подошли по технологиям, что случалось на прошлых объектах, где
границы работ. Всё, что она вернула, проходит проверку, и она же видна
оператору:

* действие не из каталога — отбрасывается с причиной («модель его выдумала»);
* шаг, кладущий файл на чужой хост, остаётся воздействием при любом ответе
  модели — класс считает код, а не она;
* необратимые шаги в очередь ставятся, но очередью и остаются: без вашего
  явного одобрения они не выполняются (дверь `agent.execute` в код, не в
  настройки). Внутренние шаги не ставятся до записи доступа — после записи
  ставятся, и всё равно ничего не делают на объекте: агент готовит команды;
* если ответ не разобрался, модель молчит или упала — работает прежний
  планировщик по правилам, и оператор видит, что именно произошло. Молчаливого
  «как будто модель предложила» здесь нет;
* оба плана — модели и правил — остаются в базе: без этого «модель планирует
  лучше» нечем проверить.

По умолчанию режим прежний, без модели (`ASM_PLANNER=rules`). Включить:
`ASM_PLANNER=model` (только модель, при неудаче — правила) или `both` (модель,
остаток добирают правила). Разовая проверка:
`python3 app.py agent extend <сессия> --scan <скан> --planner model`, журнал
обоих планов — `python3 app.py agent plans <сессия>`.

**Чат с агентом: рабочий стол сессии.** Вы работаете с моделью разговором, а
инструменты она берёт сама. Пункт 4 порядка §27.7 («панель-рабочий стол»):
слева — ход работы, в центре — диалог, справа — контекст; одобрения — карточками
прямо в ленте.

```bash
python3 app.py chat 3                 # разговор в терминале (сессия 3)
python3 app.py chat 3 --ask "что видно по объекту?"   # одна реплика
python3 app.py attach 1 ./снимок.png  # приложить файл или фото к объекту
# в браузере: python3 app.py serve  → кнопка «💬 Чат с агентом» или http://127.0.0.1:8000/chat
python3 app.py mcp --session 3        # те же инструменты наружу, по MCP (только чтение)
python3 app.py mcp --status           # что отдаём наружу, а что закрыто
```

**Инструменты наружу по MCP — только чтение.** Если работаете в редакторе вроде
OpenCode, он может подключить наши инструменты к себе:

```json
{"mcp": {"asm": {"type": "local",
                 "command": ["python3", "app.py", "mcp", "--session", "3"]}}}
```

Наружу уходят 11 инструментов чтения (карта, находки, сверка, память, знания,
состояние, арсенал, стелс, бюджет, транспорт, вложения). **Закрыты двое:**
`команда` (свободный шаг ставит человек — решение по шагу принимает оператор,
а не редактор) и `интернет` (выход наружу — это след, он должен быть решением
человека). Отказ приходит словами, а не пустотой. Подробности — §43 плана.

Что делает ASM, а что требует вашего решения:

* **Локальное чтение**: карта, находки, сверка из кэша, память, знания и состояние
  сессии. Это чтение локальной базы; содержимое объекта не считается инструкцией.
* **Каждый шаг к объекту ждёт подтверждения**: DNS, веб-проба, порты, TLS и
  свободная команда проходят ворота, попадают в карточку и не исполняются до
  явного решения оператора. Read-only запрос тоже может оставить след; очередь
  не является разрешением. Старый `ASM_CHAT_AUTO=recon` больше не включает автостарт.
* **Интернет**: только по явному поручению и через `asm/websearch.py`; адреса,
  имена хостов и секреты наружу не уходят, результат недоверенный. Для нового
  домена вендора сначала требуется отдельное решение оператора.
* **Методические подсказки**: к чату автоматически добавляются только плейбуки,
  совпавшие с признаками последнего завершённого скана. Это справочный контекст,
  не разрешение на действие; сырые prompt-файлы тестовых задач не загружаются.
* **Облачная модель**: UI заранее сообщает, что в Tokify уйдут system prompt,
  запрос, история, контекст, автоматические подсказки и выбранные вложения.
  Поведение провайдера по журналированию/обучению не предполагается без проверки.
* **Файлы и фото**: фото уходит в модель изображением (vision), текст — текстом,
  PDF/архивы — с честным отказом, если нечем разобрать; ничего не исполняется.
* **Тишины не бывает**: модель не задана, промолчала или упала — в ленте причина словами.

В терминале: `/файл <путь>`, `/файлы`, `/карта`, `/кто`, `/стоп`, `/выход`.
Инструменты: карта, находки, сверка, память, знания, состояние, арсенал, стелс,
вложения, **команда**, **бюджет**, транспорт, интернет, днс, веб-проба, порты, tls.

**Свободный шаг: метод не из каталога (06.10.2026).** Агент не обязан выбирать шаг
из готового списка — он может предложить свой способ: инструмент, связку,
параметры, свой скрипт разбора. Рамку проверяет код, а не автор шага: класс
считает **содержание** команды (чтение и пробы — `observe`/`probe`, запись и
непонятное — `impact`), самоурон (`rm -rf /`, `mkfs`, `curl … | sh`) отсекается
отдельно, ворота смотрят каждый шаг **дважды** — при постановке и на исполнении.

```bash
# терминал: агент предлагает команду и говорит, зачем она
python3 app.py agent free 3 --cmd "dig +short example.org" --intent "проверить DNS" --tool dig
# из чата то же самое инструментом «команда»: {"команда": "…", "зачем": "…"}
```

Любой свободный шаг — включая чтение и пробы — встаёт карточкой оператору и
ждёт явного одобрения. Что может уронить сервис или заблокировать учётные записи
заказчика, дополнительно проверяется воротами и остаётся запрещённым без отдельного
основания; очередь сама по себе не даёт права на запуск.

**Куда идёт шаг, решает адрес, а не класс.** Без адреса объекта шаг исполняется у
нас (наши скрипты разбора, связки движков); с адресом — уходит на объект
транспортом: соединение открываем мы, один хост на шаг, **каждая команда заново
проходит ворота на отправке**, ничего на хост не кладём. Если отправить нельзя —
первой строкой причина (`ASM_INWARD=off`, нет ssh/PowerShell, нужен пароль) и
команда целиком для ручного запуска.

```bash
python3 app.py agent free 3 --cmd "uptime" --intent "как давно хост поднят" \
    --target-host 10.0.0.5      # уйдёт на объект транспортом
python3 app.py agent free 3 --cmd "python3 разбор.py --из базы" --intent "разобрать добытое"
                                # останется у нас
```

**Класс считается содержанием и разбором, а не подстрокой:** у каждого сегмента
команды берётся программа — запись (`rm`, `chmod`, `-delete`, `sed -i`, запись в
файл) даёт `impact` с указанием, что именно; чтение (`cat`, `uptime`, `find`, `ss`,
`nmap`) — `observe`/`probe`; незнакомая программа — «содержание не опознано,
решает человек», а не «воздействие» (это была бы неправда о команде).

**Бюджет работ: агент считает и подстраивает сам.** Хосты на сессию, шаги и шум в
час (веса 1/3/9 у низкого/среднего/высокого следа), одновременно файлов на объекте
(не больше одного). Цифры предлагаются из срока сессии, размера области,
критичности заказчика, режима и прошлых сессий — **всегда с основанием**. Дальше
бюджет живёт сам: расход видно, при исчерпании шаг останавливается **с причиной**
и подсказкой, при шуме агент сжимается, при простое расширяется (в границах
0.5×…2×), каждое изменение — в журнал и в память сессии.

```bash
python3 app.py agent budget 3                     # показать: цифры, расход, основание
python3 app.py agent budget 3 --noise 20 --steps 8  # сказать «шире» вручную
```

**Транспорт внутрь: команды уходят сами.** Windows — родной PowerShell Remoting
(ничего не ставим, отпечаток Microsoft), Linux — OpenSSH. Соединение всегда
открываем мы; обратных соединений, слушателей и маячков нет, туннели остаются
ручным решением. Файл на хосте: перенос → запуск → **уборка в том же соединении**,
имя файла конкретное, запись в пакет передачи и отметка уборки — автоматически.

```bash
python3 app.py agent run 3 --secret-prompt        # пароль спросят скрытно
ASM_INWARD_KEY=~/.ssh/id_ed25519 python3 app.py agent run 3   # по ключу (для Linux)
# в панели — та же кнопка «выполнить», пароль вводится в поле и нигде не хранится
```

Настройки: `ASM_INWARD=on|off` (по умолчанию `on`), `ASM_INWARD_METHOD=auto|winrm|ssh`,
`ASM_INWARD_KEY`, `ASM_INWARD_PORT`, `ASM_INWARD_TIMEOUT`, `ASM_INWARD_PULL=1`
(разрешить забирать файлы, которые создал шаг: нужно для сбора AD). Каждая
команда проходит ворота **заново на отправке**; когда отправить нельзя — шаг
выдаёт команды текстом и называет причину первой строкой.

**Команды внутреннего шага пишет модель.** Планировщик выбирает шаг из каталога, а
что именно запустить на хосте под названной учётной записью — пишет модель, если
она подключена. Так команды идут под **этот** объект: что уже известно о версиях,
группах и хостах, а не «вообще». Границы жёсткие и проверяются кодом, а не
обещанием:

* **порядок работ, перенос файла, имя файла на хосте и уборка — код, не модель**:
  иначе уборка разошлась бы с тем, что реально лежит в чужой файловой системе;
* **каждая команда проходит ворота поимённо**: заблокированная в текст не
  попадает вовсе — вместо неё пометка «отброшено, причина». Готовый текст идёт
  через ту же проверку ответа, что и в прогонах;
* **оператор видит команды до одобрения** (`agent plan`, `agent step <номер>`):
  одобрять вслепую нечего;
* **ничего не выполняется**: шаг, как и раньше, — текст для человека;
* **модели нет, ответила мусором или упала** — команды готовятся правилами, и в
  тексте шага сказано, что это правила и почему. Тишины вместо содержания нет.

Переключатель — `ASM_MODEL_CMDS`: `auto` (по умолчанию — работает, если задан
`ASM_LLM_BASE`), `on`, `off`.

```bash
python3 app.py agent plan 1                          # команды в описании внутреннего шага
python3 app.py agent step 5                          # перечитать команды шага
python3 app.py --set ASM_MODEL_CMDS=off agent plan 1 # только правила
```


**Режим работ: одним словом.** Настроек 128, и для настоящей работы их надо
согласовать между собой. Режим хранится в базе (в PowerShell переменные между
командами не живут) и действует на каждую следующую команду:

```bash
python3 app.py mode            # что сейчас
python3 app.py mode check      # готовность машины: что мешает, что принять осознанно
python3 app.py mode combat     # боевой
python3 app.py mode safe       # тихий (откат не блокируется ничем)
```

* `safe` — тихий: щадящие скорости, план по правилам, скрытность выключена.
* `combat` — боевой: скорости pentest-профиля, план строит модель с подстраховкой
  правилами, скрытность в режиме «предупреждать о неприкрытом выходе», очередь
  на подтверждение разрешена целиком.

Перед включением боевого режима идёт проверка: самопроверка кнопки СТОП на этой
машине, наличие основных движков, ответ ли модель, прикрыт ли выход. Есть
блокеры — режим не включится (`--force` — осознанно, с записью в журнал).
Явная настройка всегда сильнее режима: `--set ASM_PROFILE=full` перекрывает
режим на один запуск. Шумное (перебор путей, сети организации, проверка
живости ключей) режим **не включает** — это решения на конкретную работу.

## 6а. Ворота, память решений и автопилот (05.10.2026)

Три слоя обвязки вокруг модели. Порядок не случаен: сначала то, чего модель
**не может**, потом то, что она **помнит**, и только потом то, что она делает
**сама**.

**Ворота (`asm/gate.py`)** проверяют текст шага и кода и дают три исхода:
`allow` — можно; `warn` — можно, но оператор видит, чем платит; `block` — не
выполняется, причина называется. Блокируются: обратное соединение/канал
управления, персистентность, очистка и подмена журналов, выгрузка данных
заказчика, перебор учётных данных, вредоносное ПО и слежка за людьми.
Предупреждают: риск уронить сервис и адрес вне согласованной области.
Проверка стоит в трёх точках — предложение шага, план модели, выполнение, —
поэтому шаг не может «проскочить» мимо неё. Промпт при этом остаётся
уговором: право спорить он держит, границы — нет.

```
python3 app.py agent gate 12          # что скажут ворота про шаг 12
ASM_SCOPE="10.0.0.0/24,corp.local"    # согласованная область: чужие адреса видны
```

**Память сессии (`agent_notes`)** — цели словами заказчика, запреты («эту
панель не трогать»), решения оператора, события. Она уходит в каждую подсказку
модели отдельным блоком, запреты — первыми. Решения по шагам записываются
сами; слова оператора — так:

```
python3 app.py agent say 3 "эту панель заказчика не трогай — боевая система"
python3 app.py agent notes 3          # что агент помнит по этой сессии
```

**Автопилот (`planner.autopilot`)** ведёт круги: выполнить одобренное →
спланировать → поставить законную часть в очередь → остановиться там, где
решает человек. Сам одобряет только наблюдение и чтение (и только если так
сказал оператор: `--approve-what recon`), никогда — воздействие, внутреннюю
работу и шаги, оставляющие файл на объекте. Останавливается на kill switch,
закрытой сессии и **на получении доступа**: дальше работа руками.

```
python3 app.py agent autopilot 3 --rounds 3 --approve-what recon
```

Всё то же есть в панели: ворота у каждого шага (у заблокированного кнопки
«одобрить» нет — рамку снимают в терминале, осознанно), память сессии на
экране, поле «сказать агенту», кнопки «Спланировать заново» и «Автопилот».

**Автономия в рамках (06.10.2026, §41).** Автопилот — не «делает что хочет»:
он ищет **лучший путь** (метод не из каталога, см. «свободный шаг» выше), но
всё, что может уронить сервис заказчика или заблокировать учётные записи, —
только с одобрением, даже когда оператор включил `--approve-what recon`. Три
точки всегда за человеком: **рамка мешает** (снимает только оператор), **риск для
доступности** (одобрение), **цель достигнута** (стоп и передача доступа).
Бюджет работ (шаги/час, шум/час, хосты, файлы на объекте) агент считает сам, сам
же его подстраивает и показывает основание — см. «Бюджет работ» ниже.

**Проверка ответа, полученного снаружи** (чат LM Studio, чужой прогон) — тем же
конвейером, чтобы судить не на глаз:

```
python3 app.py agent check 3 --file "ответ-модели.txt"
```

Печатает: какие шаги прошли бы в план, что отброшено и почему, что говорят
ворота и правила очереди, есть ли в тексте приёмы, которых мы не делаем, и —
отдельным разделом — **сверку сведений**: применимость каждой названной
уязвимости по диапазону версий, свежесть скана, источник и дата у каждого
факта. Ошибку «поверил отчёту сканера вместо диапазона версий» находит машина,
а не глаз. Сложная задача для такой проверки лежит в
`knowledge/prompts/hard-task.md`.

Лист сверенных фактов по объекту — отдельно (по умолчанию только кэш, без сети):

```
python3 app.py agent facts 3          # что мы знаем по объекту и откуда
python3 app.py agent facts 3 --net    # разово спросить NVD и пополнить кэш
```

Режим сверки: `ASM_FACTS_NET=off` — ничего не подтверждать, `cache` (по
умолчанию) — читать кэш, `allow` — разрешить запросы к источникам из списка в
коде. Источники сведений и то, что слой считает сам, описаны в `ПЛАН.md` §32.

## 7. Ограничения метода (то, что нужно знать перед показом заказчику)

* **Ложноположительные по CPE.** В дистрибутивах Linux уязвимости часто закрываются backport-патчами
  без смены версии — по базе NVD компонент «уязвим», фактически — нет. Каждую находку P0/P1
  подтверждайте вручную перед работами. (В прототипе для этого есть второй фильтр диапазонов и
  таблица `REFINED_RANGES` в `asm/cve.py` — расширяйте её по мере практики.)
* **NVD бывает неточен.** Иногда диапазон версий задан слишком широко; в прототипе такие записи
  фильтруются повторной локальной проверкой, а самые известные — уточняются вручную.
* **Свежесть данных об открытых портах.** InternetDB — снимок, может отставать на дни/недели.
* **Не видно того, что закрыто.** Если сервис за VPN или требует авторизации, пассивный анализ
  его не покажет — для этого нужен активный пентест по отдельному согласованию.
* **EPSS/KEV меняются.** В отчёте фиксируется дата анализа.

## 8. Как это встроить в ваши заказы

1. **До работ.** Письменное разрешение: домены/IP, срок, кто со стороны заказчика отвечает.
   В инструменте это обязательные поля `заказчик` + `основание`; без них анализ не запустится,
   а каждый запуск пишется в журнал аудита (кнопка «Журнал» в дашборде). Для подрядчика в РФ это
   не бюрократия, а разделение «аудита» и ст. 272 УК РФ.
2. **Первый анализ** — 5–15 минут для небольшой компании. Результат: отчёт .md для заказчика,
   .csv для трекера, .json для интеграций.
3. **Повторные анализы** раз в 2–4 недели: раздел «Изменения» показывает новые активы и новые
   находки, а также закрытые. Это то, за что берут абонентскую плату — контроль, а не разовый отчёт.
4. **Допродажа.** Отчёт даёт естественный список работ: обновление компонентов, закрытие БД/VPN,
   вынос тестовых сред, аудит доступа к панелям, резервное копирование.

## 11. Что добавлено во второй итерации (04.10.2026)

**Сканирование всей инфраструктуры по одному адресу (`estate.py`).**
Вводите один адрес — инструмент сам добирает остальное: типовые имена (словарь из ~120 вариантов),
почтовые и служебные хосты из NS/MX, домены из SPF, обратные имена для IP,
а по флагу «сети организации» — анонсированные префиксы автономной системы адреса и ближайшие к
подтверждённым адреса из этих сетей (с предупреждением: сети могут содержать чужие адреса).
Лимиты: `ASM_ESTATE_WORDS`, `ASM_ESTATE_MAX_HOSTS`, `ASM_ESTATE_MAX_PREFIXES`,
`ASM_ESTATE_PREFIX_IPS`, `ASM_ESTATE_MAX_EXTRA_IPS`, включение — `ASM_ESTATE=1`, сети — `ASM_ESTATE_ASN=1`.

**Клик по элементу → карточка → разговор.** Граф: поиск, масштаб, перетаскивание узлов,
сохранение расположения, сохранённые виды, подсветка «путей до риска» (кратчайшие маршруты от
точек входа до узлов с находками P0/P1). Карточка: находка, актив, порт, сервис и **кнопка
«Проверить заново»** — точечная перепроверка своего же адреса (свежий ответ сервера прикладывается
к журналу аудита) и **«Мнение ИИ»** — структурированный вердикт «подтверждено / ложное /
недостаточно данных» с указанием, чем подтвердить.

**Триаж и дисциплина работы.** Статусы находок (открыто, подтверждено, ложное, принято в риск,
закрыто) с пометкой и ответственным; статусы и отпечаток доказательства переносятся на повторные
анализы, исчезнувшие находки помечаются закрытыми автоматически. Реестр активов: критичность,
доступ, ответственный, метки, заметка — **критичность актива двигает приоритеты его находок**
(контекст бизнеса, как в SSVC).

**Процесс.** Планировщик регулярных анализов (`/api/schedule`, интервал в интерфейсе), уведомления
(Telegram/webhook — выключены по умолчанию), «Сводка для руководителя» на один экран.
Поиск по находкам переведён на полнотекстовый FTS5 с запасным вариантом по подстроке.

**ИИ-модуль.** Поток SSE (`context` → `token` → `done`), ограничение частоты, очистка недоверенного
текста (HTML-комментарии, невидимые символы, пометка фраз-инъекций), история разговора в базе,
строгие JSON-ответы для триажа, офлайн-режим без модели.

Проверки этой итерации: `python3 -m unittest discover -s tests` — 13 тестов (на момент той итерации; текущий набор — 221); живой анализ №12
(195 находок, перенос статусов и ответственного, 159 переоценённых по критичности активов,
FTS-поиск, маршруты до риска, точечная перепроверка, защита от проверки чужих адресов).

## 11д. Что убрано из отчёта заказчику (03.10)

Отчёт читает не инженер, а руководитель заказчика — поэтому из текста вычищено всё, что
выдаёт «внутренности» платформы:

- **Никаких путей на машине аудитора.** Раньше в графе «Объект» можно было увидеть
  `/tmp/asm-repo-gyhecgum/repo/package-lock.json`; теперь — `package-lock.json`. Копия

  «CVE-2021-40438 — 45.33.32.156:80», не более 12 пунктов на блок, остальное — «…и ещё N».

  `…/nosuchurl/><script>alert` — это следы проверок, а не новые сервисы заказчика;

## 11г. Как запускается анализ из командной строки (03.10)

`python3 app.py scan <цель>` **ждёт до конца** — это поведение по умолчанию, потому что в
99 % случаев от анализа хотят результат, а не «команда завершилась успешно».

- `--no-wait` запускает анализ **отдельным процессом** (журнал пишется в `scan-<номер>.log`
  рядом с проектом). Это не «нить внутри команды»: раньше нить умирала вместе с командой,
  а запись скана оставалась в состоянии «идёт» навсегда — казалось, что анализ идёт, хотя
  не шло ничего. Теперь процесс настоящий и отделён от терминала.
- Число в `scan` — это **ID цели**. Если ввести ID скана, команда скажет об этом прямо и
  подскажет номер цели.
- Сканы, оставшиеся в статусе «идёт» после перезапуска окружения, при следующем старте
  панели помечаются как **прерванные** (процессы сканов перезапуск не переживают) — в
  интерфейсе у них своя подпись и подсказка «запустите заново», чтобы это не выглядело
  как ошибка самой проверки.

## 11в. Почему арсенал живёт в `build/tools`, а не в `~/.cache` (04.10)

Это не мелочь, а условие того, чтобы проект вообще сохранялся между сессиями.

- Каталоги **вне** папки проекта (`~/.cache/asm-tools`) окружение стирает при перезапуске —
  арсенал исчезал.
- Но если положить все 19 инструментов **в** проект, снимок workspace раздувается:
  13 742 шаблона nuclei + правила Semgrep + сам trivy = **914 МБ и 20 869 файлов**
  при лимите 128 МБ / 10 000 файлов. Снимок перестаёт сохраняться: теряется всё, включая код.
- Решение: арсенал ставится в `<проект>/build/tools` — **внутри** проекта (значит,
  восстанавливается и не теряется), но под именем `build`, а такие каталоги в снимок
  не включаются по определению. В снимке остаются код, документы, база результатов
  и словари: **1 402 файла / 35 МБ**.
- Служебные кэши движков (`PDCP_DIR`, `NUCLEI_CACHE_DIR`, `XDG_CACHE_HOME`, сессии Wapiti)
  тоже уведены в `build/tools` — домашний каталог больше не мусорится, а `cpan`-кэш
  (43 МБ) заменён точечной установкой модуля `XML::Writer` прямо в каталог арсенала.
- Восстановление после перезапуска — одна команда (её же видно в подсказке при старте):
  `bash bin/install-tools.sh` (полный) или `--fast` (ядро). Установка идемпотентна:
  уже стоящее не перекачивается, а частично распакованный набор шаблонов (после обрыва)
  определяется как неполный и докачивается.

## 12. Правило безопасности (одно, короткое)

**Дашборд слушает все интерфейсы (`0.0.0.0`) и не требует аутентификации** —
это решение заказчика, а не недосмотр: он работает в доверенной сети. Условие
важное, потому что само по себе выглядит ошибкой, и через полгода это легко
«починить» не разобравшись. Два следствия:

- ставить дашборд только в закрытой сети; на машине с публичным адресом
  `0.0.0.0` означает, что интерфейс открыт всем, кто до неё дотянется;
- всё, что дашборд показывает, — это находки по объекту заказчика, то есть
  карта его периметра. Права на её чтение ограничиваются сетью, а не паролем.

Активные проверки (сканирование портов и шаблонные проверки) допустимы **только** для
инфраструктуры, на которую у вас есть разрешение владельца — письмо или договор. Пассивный
анализ открытых источников разрешения не требует. Эксплуатация найденного и перебор паролей
инструментом не выполняются и добавляться не будут.

## 13. Работа в Windows (Git Bash)

Инструмент запускается из **Git Bash** (MINGW64) поверх PowerShell. Различия
ниже не косметические: часть из них однажды уже привела к ложному «движка нет»,
поэтому они собраны в одном месте.

**Переменные окружения.** `ASM_X=1 python3 app.py …` в Git Bash не работает:
подстановку перехватывает `cmd.exe`, и переменная до процесса не доходит. Все
настройки (сейчас 127 — точное число печатает `--settings`) задаются ключом:

```bash
python3 app.py scan 12 --set ASM_PROFILE=pentest
python3 app.py --settings                  # что вообще можно задать
python3 app.py serve --port 8787           # --port/--host есть только у serve
```

**Если `python3` открывает Microsoft Store** — это заглушка Windows, а не
интерпретатор. Используйте `py -3` или отключите псевдоним в «Параметры →
Приложения → Дополнительные компоненты».

**Движки и `.exe`.** Арсенал ставится нативными Windows-сборками с суффиксом
`.exe`. Ловушка MSYS: `[ -f tools/bin/nuclei ]` отвечает «да», когда на диске
лежит `nuclei.exe` — и удаление «старой копии» уносит рабочий движок. Поэтому
установщик ищет файлы в порядке `имя.exe → имя.cmd → имя`, а удаляет старьё
через саму Windows, а не через `rm`.

**nmap.** Ставится официальным установщиком (`npcap` + `nmap` setup): portable
сборка для Windows останавливается на версии 7.92. Ключ `/S` молчаливый только
у OEM-инсталлятора, у обычного откроется окно — это нормально, установку нужно
подтвердить.

**Модель (ИИ-слой и поиск по смыслу).** Ставится PowerShell-скриптом:

```bash
powershell -ExecutionPolicy Bypass -File bin/install-llm.ps1
python3 bin/llm-bench.py        # замер на своих промптах, а не на чужих числах
```

**Кириллица в консоли.** CLI переводит консоль в UTF-8 сам (то же, что
`chcp 65001`) и просит utf-8 у потоков вывода — «кракозябр» быть не должно ни
в PowerShell, ни в Git Bash. Если мусор всё-таки виден (например, в старом
`cmd.exe` с кодировкой 866) — запасной путь `export PYTHONUTF8=1` в текущей
сессии Git Bash: эта переменная нужна Python до старта, а не приложению.

**Панель и проверка готовности.** Обе команды рассчитаны на первый запуск без
подготовки:

```bash
python3 app.py serve --port 8787   # --port/--host есть только у serve
python3 app.py mode check          # СТОП, арсенал, модель, панель, выход наружу
```

Если порт занят (на Windows его часто держит прежняя панель, окно которой уже
закрыто) — `serve` скажет это словами и предложит соседний порт, а `mode check`
покажет «панель: порт занят» с готовой командой. При первом запуске Windows
спросит про брандмауэр — разрешите для частных сетей, если панель нужна с
другого компьютера; закрывается панель по Ctrl+C.

**Остановка.** «СТОП» в дашборде и `app.py agent stop` убивают дерево процессов
движков: на Linux — по группе процессов, на Windows — `taskkill /T /F` по
списку потомков из `tasklist`.

> **Что на Windows ещё не проверено — и это важно.** Принудительная остановка
> (`taskkill`), распаковка архивов внутри установщика и поведение переносимых
> на цель файлов (`pspy`, `chisel`) написаны, но на живом Windows не гонялись.
> Проверка — два прогона на самой машине (второй входит и в `mode check`):
>
> ```bash
> bash bin/install-tools.sh --selftest
> python3 app.py agent selftest
> ```
>
> До этих прогонов считайте перечисленное непроверенным, а не рабочим: на
> Linux оно работает, на Windows вероятность ошибки в пути или в имени процесса
> выше обычной.

**Где что лежит.** Проект — `C:\Users\<вы>\Documents\Arena\asm`, база
`asm.sqlite` рядом с ним, арсенал — `build/tools` (`bin/` — запускается с этой
машины, `payloads/` — переносится на цель). Список перенесённых файлов нужен для
уборки после работ, поэтому имена файлов и есть подпись.
